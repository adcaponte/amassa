<objective>
Criar o segundo Postgres — o de testes — antes de existir qualquer etapa de teste ponta a ponta no
pipeline. A ordem importa: o passo de E2E do plano 01-05 depende deste banco, e inverter a ordem
produz um pipeline que passa sem nunca ter tocado num banco de verdade.

Purpose: a separação é **física**, não uma convenção de nome (D-09). Um serviço Postgres separado,
com volume efêmero, significa que um teste que apaga tudo não tem como encostar no banco real. Uma
convenção de nome dentro da mesma instância depende de ninguém errar uma string de conexão — e
alguém sempre erra, uma vez, no pior dia.

Output: `docker/compose.teste.yml` com o serviço `postgres_teste`, Playwright configurado para
desktop e celular, o teste ponta a ponta da fundação, e a prova de que um teste quebrado derruba o
comando.
</objective>

  <action>
Escrever `docker/compose.teste.yml` como arquivo próprio, separado, contendo um único serviço
chamado `postgres_teste`. Ele usa a mesma imagem oficial e a mesma versão do Postgres de produção —
testar contra uma versão diferente da de produção é testar outro sistema. Credenciais e nome de
banco próprios, distintos dos de produção, para que uma string de conexão trocada por engano falhe
alto em vez de escrever no lugar errado.

O armazenamento é `tmpfs` montado em `/var/lib/postgresql/data`: o banco vive em memória e some
quando o contêiner morre. Não declarar volume nomeado nem bind mount. Sem publicar porta no host
e sem política de reinício.

Este arquivo **não** é referenciado por `docker/compose.yml` e nunca é copiado para o servidor. O
compose do servidor não contém serviço de teste (D-11); se um dia for preciso rodar E2E contra o
ambiente real, isso volta como decisão própria.

Acrescentar `DATABASE_URL_TESTE` ao `.env.example`, sem valor, e o script `test:e2e` ao
`package.json`, que aplica as migrações contra o banco de teste e em seguida roda o Playwright.
Conferir que `.gitignore` já cobre `playwright-report/` e `test-results/`; acrescentar apenas o
que faltar.
  </action>

  <action>
Instalar o Playwright como dependência de desenvolvimento e escrever `playwright.config.ts` com
dois projetos: um navegador desktop e um viewport de celular, porque o sistema é usado em pé, no
ateliê, numa tela de 6 polegadas — testar só no desktop não mede o que importa.

O `webServer` do Playwright sobe a build real (`npm run build` seguido de `npm run start`), não o
servidor de desenvolvimento: a build é onde as variáveis com prefixo `NEXT_PUBLIC_` são embutidas,
e testar contra o modo de desenvolvimento esconderia exatamente a classe de falha que esta fase
existe para prevenir. `DATABASE_URL` do processo do servidor recebe o valor de
`DATABASE_URL_TESTE`. Sem reuso de servidor existente na integração contínua.

Escrever `tests/e2e/fundacao.spec.ts` com dois casos, ambos rodando nos dois projetos:
a página inicial responde 200 e mostra o nome `AMASSA` e a frase declarada em `FRASE_NO_AR`; e
`/api/health` responde 200 com um corpo em que o campo do banco está em ordem. O segundo caso é o
que dá sentido ao banco de teste — sem ele, o E2E não tocaria no Postgres e o serviço separado
seria decoração.

Provar o portão: inverter temporariamente uma expectativa do arquivo de teste, rodar `test:e2e`,
confirmar que o comando sai com código diferente de zero, e desfazer a inversão antes do commit.
É esse comportamento que o pipeline do plano 01-05 vai usar para barrar um deploy com teste
quebrado (INFRA-07); se o comando saísse com zero, o portão do pipeline seria decorativo.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| suíte de testes → banco | um teste roda com privilégio total sobre o banco que alcançar; qual banco ele alcança é a fronteira |
| banco de teste → host | dados de teste não devem sobreviver nem ser acessíveis de fora |

## STRIDE Threat Register
