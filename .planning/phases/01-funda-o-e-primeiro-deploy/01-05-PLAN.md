<objective>
Fechar o caminho automático entre `git push` na `main` e uma imagem publicada e implantada, com
portões que barram de verdade. O pipeline é a única coisa entre um teste quebrado e o site fora do
ar, e é onde a armadilha mais provável do projeto — variáveis com prefixo `NEXT_PUBLIC_` embutidas
no `next build` — precisa ser resolvida, porque é aqui que a imagem é construída.

Purpose: a imagem nasce no GitHub Actions e não no servidor porque um `next build` consome bastante
RAM; se estourar a memória do VPS durante uma publicação, o site cai — e cai junto com o banco, que
agora mora na mesma máquina. O runner constrói, o servidor só baixa artefato pronto.

Output: `.github/workflows/entrega.yml` com quatro jobs encadeados, publicação no GHCR, deploy por
SSH nomeando o serviço `app`, e a prova executada de que um teste quebrado não vira imagem
publicada.
</objective>

Escrever `.github/workflows/entrega.yml`, disparado por push na `main` e por acionamento manual,
com um grupo de concorrência que cancela execuções sobrepostas — dois deploys simultâneos na mesma
máquina é uma corrida sem vencedor. Permissões mínimas no topo: leitura de conteúdo e escrita de
pacotes, nada além disso.

Quatro jobs encadeados por `needs`, nesta ordem:

`qualidade` — instala dependências com `npm ci` e roda `npm run lint` e `npm test`. É o portão mais
barato e vem primeiro.

`e2e` — depende de `qualidade`. Declara o Postgres de teste como *service container* do runner,
com a mesma imagem e versão do banco de produção, sem publicar porta para fora do runner. Define
`DATABASE_URL_TESTE`, aplica as migrações contra ele, instala os navegadores do Playwright e roda
`npm run test:e2e`. O E2E roda **só aqui**, no GitHub Actions (D-10): o VPS não carrega peso extra e
o pipeline continua sendo o único portão antes da publicação.

`imagem` — depende de `e2e`. Faz login no GHCR com o token efêmero do próprio runner, e constrói e
publica duas tags a partir do mesmo `docker/Dockerfile`: o alvo `app` e o alvo `ferramentas`, sob
`ghcr.io` com o dono do repositório e o nome `amassa`. O alvo `app` recebe `NEXT_PUBLIC_SITE_URL`
como **build-arg**, lido de uma variável do repositório — nunca como variável de runtime. Variáveis
com esse prefixo são embutidas no JavaScript durante o `next build`; como a imagem é construída
aqui e o arquivo de ambiente vive no VPS, tratá-las como runtime faz tudo funcionar em `localhost`
e falhar em produção. `DATABASE_URL` e `AUTH_SECRET` não aparecem em lugar nenhum deste job.

`implantar` — depende de `imagem` e só executa quando a variável de repositório `DEPLOY_ATIVO` vale
`true`, que é o que o dono liga depois de preparar o servidor no plano 01-07. Conecta por SSH
usando os secrets `VPS_HOST`, `VPS_USUARIO` e `VPS_SSH_CHAVE`, entra em `/opt/amassa` e executa
`docker compose pull app` seguido de `docker compose up -d app`. O nome do serviço é obrigatório:
o comando sem ele recria o contêiner do Postgres a cada publicação. Fecha verificando `/api/health`
pelo domínio e falhando se a resposta não vier em ordem.

Nenhum passo deste workflow aplica migração. Migração é aplicada à mão, depois de um backup, por
alguém que está olhando o resultado — uma migração ruim disparada por um push acidental não tem
desfazer, e agora o banco é nosso.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull request de terceiro → runner | repositório público: qualquer pessoa pode abrir PR e propor código que o runner executaria |
| runner do GitHub Actions → GHCR | o runner tem permissão de escrita em pacotes |
| runner do GitHub Actions → VPS por SSH | canal de deploy; a chave privada vive como secret |
| build da imagem → imagem pública | tudo o que entrar na imagem fica visível para o mundo |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-19 | Elevation of privilege | job `implantar` disparado por PR de terceiro | high | mitigate | Os jobs de publicação e deploy só rodam em push na `main`; secrets não são expostos a execuções de PR de fork, e o job `implantar` ainda exige `DEPLOY_ATIVO` |
| T-01-20 | Information disclosure | secrets no log do workflow | high | mitigate | Nenhum passo imprime variável de ambiente; permissões declaradas no topo com escopo mínimo; `AUTH_SECRET` e `DATABASE_URL` de produção não aparecem em nenhum job |
| T-01-21 | Spoofing | portão de qualidade | high | mitigate | `imagem` depende de `e2e`, que depende de `qualidade`; provado empiricamente com um teste quebrado numa branch, confirmando que nada é publicado |
| T-01-22 | Tampering | banco de produção por migração automática | critical | mitigate | Nenhum passo do workflow aplica migração; verificado por gate no arquivo do workflow. Migração é operação manual, após backup, no plano 01-03 |
| T-01-23 | Denial of service | `docker compose up` sem nomear serviço no passo de deploy | high | mitigate | Gate comparando a contagem de ocorrências com e sem o nome do serviço — nenhuma ocorrência sem `app` |
| T-01-SC | Tampering | actions de terceiros usadas no workflow | high | mitigate | Somente actions oficiais do GitHub e do Docker, fixadas por versão maior; nenhuma action de autor desconhecido entra no pipeline |
</threat_model>
