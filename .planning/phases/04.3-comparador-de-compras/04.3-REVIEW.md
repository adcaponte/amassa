# Phase 04.3: Code Review Report — Comparador de Compras

**Reviewed:** 2026-09-18

## Summary

Revisei os módulos puros (`lib/cotacoes/*`), os Server Actions, as consultas, o schema/migrações e
os componentes de UI do Comparador de Compras, além dos arquivos de Abertura tocados só para
acrescentar a quarta aba. A disciplina do projeto é visivelmente seguida na parte que os testes
conseguem enxergar: todo Server Action começa por `exigirUsuario()`, toda entrada do usuário passa
por Zod no servidor com a mesma regra usada pelo cliente (nunca reimplementada), nenhuma exclusão é
silenciosa, os textos estão em português, o SQL usa parâmetros via Drizzle (nenhuma concatenação de
string em query), e não há segredo nem `console.log`/`TODO` esquecido nos arquivos revisados.

O achado mais sério (CR-01) é um caso clássico de "o código parece certo, os testes passam, mas a
tela não faz o que o comentário diz": a caixa de marcação "comparar" (`components/ui/checkbox.tsx`,
instalada nesta fase) usa classes Tailwind `data-checked:*` que nunca combinam com o atributo real
que o Radix Checkbox escreve no DOM (`data-state="checked"`). O comportamento funcional (marcar,
desmarcar, `aria-checked`) continua correto — é por isso que a suíte e2e, que só verifica
`.toBeChecked()`, não pegou o problema — mas o preenchimento visual do estado marcado nunca
acontece. Esse mesmo padrão quebrado (`data-open:`/`data-closed:`) já existe em componentes fora do
escopo desta fase (`components/ui/dialog.tsx`, `components/ui/switch.tsx`), então não é uma
invenção deste plano — mas o checkbox É novo nesta fase e está no escopo revisado, e é o controle
central do fluxo "marcar para comparar" (D-13), por isso registro como bloqueador aqui.

Os demais achados são de robustez de estado de cliente (a marcação de comparação se perde em
qualquer gravação, não só ao trocar de categoria) e de código morto/duplicado de baixo risco — a
maior parte já reconhecida pela própria equipe no SUMMARY do plano 05.

## Critical Issues

### CR-01: A caixa "marcar para comparar" nunca mostra visualmente o estado marcado

**File:** `components/ui/checkbox.tsx:17` (consumida por `components/amassa/cotacoes/marcar-cotacao.tsx:30`)
**Issue:**
O `Checkbox` usa classes Tailwind como `data-checked:border-primary data-checked:bg-primary
data-checked:text-primary-foreground` para estilizar o estado marcado. Essas classes compilam para
o seletor CSS `[data-checked]` (presença de um atributo booleano literal `data-checked`) —
confirmado no CSS de produção já compilado (`.next/static/css/*.css`):

```css
.has-data-checked\:border-primary\/30:has([data-checked]){...}
```

O `CheckboxPrimitive.Root` do pacote `radix-ui` (que reexporta `@radix-ui/react-checkbox@*`,
`node_modules/@radix-ui/react-checkbox/dist/index.mjs:111`) nunca escreve um atributo
`data-checked` — ele escreve `data-state="checked" | "unchecked" | "indeterminate"`:

```js
"data-state": getState(checked),
```

Como esses dois nomes de atributo nunca coincidem, o seletor `[data-checked]` nunca casa com nada
no DOM real, e as classes de preenchimento (fundo terracota, borda, cor do ícone) nunca se aplicam.
O ícone de check em si continua aparecendo/desaparecendo (o `CheckboxPrimitive.Indicator` monta e
desmonta via `Presence`, independente de CSS), então a marcação não é 100% invisível — mas o
quadrado nunca preenche com a cor de destaque, e o ícone fica na cor de texto padrão em vez de
branco sobre terracota. Numa lista de 5-10 cotações com várias marcadas para D-13 ("Comparar
selecionados"), a diferença visual entre marcado/não marcado fica bem mais fraca do que o desenho
pretendia, e o e2e não pega isso porque só verifica `.toBeChecked()`/`aria-checked`, nunca a cor
computada.

O mesmo padrão quebrado (`data-open:`/`data-closed:` em vez de `data-[state=open]:`) já existe em
`components/ui/dialog.tsx` e `components/ui/switch.tsx` (fora do escopo desta fase) — não é uma
regressão inventada aqui, mas `checkbox.tsx` é um arquivo novo desta fase e está no escopo revisado.

**Fix:**
Trocar `data-checked:`/`data-unchecked:` por `data-[state=checked]:`/`data-[state=unchecked]:` (a
sintaxe de valor de atributo do Tailwind v4), que casa com o que o Radix realmente escreve:

```diff
- "peer relative flex size-4 shrink-0 items-center justify-center rounded-[4px] border border-input transition-colors outline-none group-has-disabled/field:opacity-50 group-has-[:focus-visible]/field-label:ring-0 group-has-[:focus-visible]/field-label:not-data-checked:border-input after:absolute after:-inset-x-3 after:-inset-y-2 focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50 disabled:cursor-not-allowed disabled:opacity-50 aria-invalid:border-destructive aria-invalid:ring-3 aria-invalid:ring-destructive/20 aria-invalid:aria-checked:border-primary dark:bg-input/30 dark:aria-invalid:border-destructive/50 dark:aria-invalid:ring-destructive/40 data-checked:border-primary data-checked:bg-primary data-checked:text-primary-foreground group-has-[:focus-visible]/field-label:data-checked:border-primary dark:data-checked:bg-primary",
+ "peer relative flex size-4 shrink-0 items-center justify-center rounded-[4px] border border-input transition-colors outline-none group-has-disabled/field:opacity-50 group-has-[:focus-visible]/field-label:ring-0 group-has-[:focus-visible]/field-label:not-data-[state=checked]:border-input after:absolute after:-inset-x-3 after:-inset-y-2 focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50 disabled:cursor-not-allowed disabled:opacity-50 aria-invalid:border-destructive aria-invalid:ring-3 aria-invalid:ring-destructive/20 aria-invalid:aria-checked:border-primary dark:bg-input/30 dark:aria-invalid:border-destructive/50 dark:aria-invalid:ring-destructive/40 data-[state=checked]:border-primary data-[state=checked]:bg-primary data-[state=checked]:text-primary-foreground group-has-[:focus-visible]/field-label:data-[state=checked]:border-primary dark:data-[state=checked]:bg-primary",
```

Recomendo verificar visualmente depois do ajuste (marcar/desmarcar uma cotação em
`/abertura?aba=cotacoes` e conferir se o quadrado preenche de terracota) — nenhum teste automatizado
hoje cobre cor computada, então esta é uma verificação manual mesmo. Vale avaliar o mesmo problema em
`components/ui/dialog.tsx`/`components/ui/switch.tsx` numa tarefa separada, já que está fora do
escopo desta fase.

## Warnings

### WR-01: Qualquer gravação em Cotações apaga a marcação "comparar", não só a troca de categoria

**File:** `components/amassa/cotacoes/painel-cotacoes.tsx:41` (consequência de
`components/amassa/cotacoes/formulario-cotacao.tsx:185`,
`components/amassa/cotacoes/confirmar-remover-cotacao.tsx:69`,
`components/amassa/cotacoes/dialogo-categoria.tsx:119`,
`components/amassa/cotacoes/confirmar-remover-categoria.tsx:74`)
**Issue:**
`marcados` (o conjunto de cotações marcadas para comparar, D-13) é `useState` dono de
`PainelCotacoes`. O comentário do componente documenta que trocar de categoria zera a marcação de
propósito, porque o componente é remontado via `key={categoriaAtiva.id}`. O que não está
documentado nem parece ter sido considerado: **toda** ação de escrita do módulo — salvar uma
cotação (`window.location.assign` em `formulario-cotacao.tsx:185`), remover uma cotação
(`confirmar-remover-cotacao.tsx:69`), criar/renomear categoria (`dialogo-categoria.tsx:119`) ou
remover categoria (`confirmar-remover-categoria.tsx:74`) — termina em navegação COMPLETA
(`window.location.assign`), que recarrega a página inteira e zera todo estado de React, incluindo
`marcados`.

Cenário real: a pessoa marca 3 cotações de fornos para comparar (D-13), entra na comparação, decide
corrigir um erro de digitação no preço de UMA delas (sem relação com as outras duas), salva — e ao
voltar para a lista as 3 marcações somem, porque a gravação disparou uma navegação completa. A
marcação para comparar é justamente o tipo de estado que vale a pena preservar através de uma
edição rápida no meio da tarefa de comparar fornecedores, e hoje isso não acontece.

Isso é coerente com a arquitetura D-23 (navegação completa de propósito, sem `toast` de sucesso) e
não chega a ser um bug de dado — é uma lacuna de robustez de UX que o desenho atual não cobre, e que
provavelmente vale uma decisão consciente do dono (ex.: aceitar a perda, ou persistir `marcados` na
URL só durante o modo comparação).

**Fix:** Documentar a decisão explicitamente (se for aceitável, um comentário ao lado de `marcados`
dizendo isso evita que pareça um esquecimento) ou, se não for aceitável, considerar carregar
`marcados` a partir de um parâmetro de URL (ex.: `?marcados=id1,id2,id3`) só quando `modo ===
"comparar"`, sobrevivendo à navegação completa das ações de escrita.

### WR-02: `cotacoesRemovidas` pode ficar impreciso sob concorrência, e hoje é ignorado por quem chama

**File:** `lib/cotacoes/acoes.ts:211-253`
**Issue:**
`removerCategoriaDeCotacao` faz, dentro de uma transação: `SELECT` da categoria, `SELECT count(*)`
das cotações dela, e só então `DELETE` da categoria (a cascata do banco apaga as cotações). Sob
`READ COMMITTED` (padrão do Postgres), cada instrução enxerga um snapshot próprio — se outra sessão
inserir uma cotação nessa categoria entre o `SELECT count(*)` e o `DELETE`, essa linha nova é
apagada pela cascata, mas não entra na contagem já lida, então `cotacoesRemovidas` sairia
subestimado em relação ao que realmente foi perdido. O comentário do código (linha 204-206) chama
essa contagem de "FONTE DE VERDADE FINAL" — o que só é verdade se nada mudar entre as duas
instruções, o que a transação não garante sozinha (faltaria `SELECT ... FOR UPDATE`/`SERIALIZABLE`
para isso).

Hoje o risco é só teórico e de baixo impacto: `confirmar-remover-categoria.tsx` nunca lê
`resposta.dados.cotacoesRemovidas` (ver INFO-03) — o valor é calculado e devolvido, mas descartado
pelo único chamador. Registro aqui porque, no dia em que esse número for exibido (um `toast`, um
log de auditoria), a imprecisão sob concorrência vai valer.

**Fix:** Se o valor passar a ser exibido, trocar o `SELECT count(*)` solto por
`DELETE ... RETURNING` sobre `cotacoes` (contando as linhas de fato apagadas) antes do `DELETE` da
categoria, em vez de contar e confiar que nada muda depois.
