# Phase 04.5 Plan 10: Fotos — upload, EXIF/GPS removido, rota autenticada Summary

**A primeira vez que a plataforma guarda um arquivo enviado por alguém: `sharp` reduz a foto a no
máximo 1600px e apaga todo metadado por padrão (nunca chamando `.withMetadata()`), `file-type`
valida os primeiros bytes antes de qualquer processamento, e `GET /api/orcamentos/fotos/[id]` —
atrás de `exigirUsuario()` — é a única porta que serve o resultado. No caminho, um achado real: o
`middleware.ts` da plataforma nunca tinha precisado distinguir "rota de página" de "rota de API",
e a primeira API autenticada revelou a lacuna.**

## Accomplishments

- **`lib/orcamentos/fotos.ts` — o pipeline de privacidade.** `validarTipoRealDaFoto` confere
  tamanho (≤ 15 MB) e depois os primeiros bytes com `file-type`, nunca a extensão nem o
  Content-Type que o navegador declarou; o caminho de recusa nunca chama `sharp`. `tratarFotoDe
  Orcamento` roda `.rotate()` sem argumento (orienta pelos pixels e descarta a etiqueta),
  redimensiona para caber em 1600px sem ampliar, converte para JPEG qualidade 82 — e **nenhuma
  chamada a `.withMetadata()`** em lugar nenhum, com um comentário grande explicando que essa é
  exatamente a chamada que reativaria o EXIF/GPS. `TIPOS_ACEITOS` é montado na carga do módulo
  perguntando à própria instalação do `sharp` o que ela decodifica — nesta máquina, a resposta foi
  "sim, HEIC/HEIF suportado" (veredito registrado no teste e no console).
- **A prova de que o GPS some é real, não vácua.** `sharp` **não** escreve um GPS IFD de verdade
  via `withMetadata({ exif: { GPS: {...} } })` — confirmado nesta sessão: a chamada não lança erro,
  mas o ponteiro de tag `0x8825` nunca aparece no IFD0 do resultado. Por isso o teste usa uma
  fixture sintética (`tests/fixtures/orcamentos-foto-com-gps.jpg`, 427 bytes) montada à mão: um
  JPEG gerado pelo próprio `sharp`, com um segmento APP1/EXIF genuíno grudado depois do SOI,
  carregando GPSLatitude/GPSLongitude como `RATIONAL` de verdade e `Orientation = 6`. O teste
  primeiro PROVA que a entrada carrega o GPS (parseando o IFD0 à mão) e só depois afirma que o
  resultado não tem `exif` nenhum — e que a largura/altura trocaram (30×40 → confirma que a rotação
  foi aplicada aos pixels antes da etiqueta sumir).
- **`anexarFotoDeOrcamento`, nesta ordem exata:** valida tipo/tamanho → trata a foto (fora da
  transação) → dentro de `db.transaction`: trava o orçamento, confere rascunho, conta as fotos e
  recusa a quarta, gera o nome (`randomUUID().jpg`), insere a linha, **e só então grava o arquivo
  em disco, ainda dentro da mesma transação** — se `fs.writeFile` falhar, o `throw` propaga e o
  Postgres desfaz o insert junto. `removerFotoDeOrcamento` faz o inverso: apaga a linha e reordena
  primeiro, e só depois apaga o arquivo, ignorando `ENOENT`.
- **`GET /api/orcamentos/fotos/[id]`** — `exigirUsuario()` dentro de `try` (401 em português, nunca
  um redirect); identificador validado por regex antes de qualquer consulta; `caminhoDaFoto()`
  (plano 03) é a única porta de montagem de caminho; `Cache-Control: private, max-age=86400`.
- **`FotosDeReferencia`** — grade `auto-fill minmax(96px,1fr)`, botão com input nativo sobreposto
  (`accept="image/*"`, sem forçar câmera), célula de espera na posição final, imagem sempre a que o
  servidor gravou, erro de tipo remove a célula sem ocupar vaga, erro de rede vira célula própria
  com "Tentar de novo" reenviando o MESMO arquivo, limite de 3 troca o botão pela frase, legenda
  editável por foto, "tirar" com `AlertDialog` controlado.
- **Achado real, corrigido nesta execução — `middleware.ts`.** O caso (c) do e2e (a rota sem
  sessão deve responder 401) revelou que o `authorized()` do Auth.js, quando nega, **sempre**
  redireciona para `/login` — inclusive para uma rota de API. Um `fetch()`/`<img>` não segue esse
  redirect de forma útil (chegaria como 200, a própria página de login). `middleware.ts` ganhou a
  regra geral: quando o Auth.js decide redirecionar E o caminho é `/api/*` não público (fora de
  `/api/health`/`/api/auth`), o middleware troca o redirect por um 401 JSON — só o formato muda, a
  decisão de `authorized()` é a mesma de sempre. Como é a primeira rota de API autenticada da
  plataforma, essa lacuna nunca tinha aparecido antes.

## Deviations from Plan

**Nenhum desvio de regra de negócio.** Dois achados reais, ambos documentados:

**1. [Rule 2 — funcionalidade crítica ausente] `middleware.ts` não distinguia rota de API de rota
de página.**
- **Encontrado durante:** verificação e2e da Tarefa 4, caso (c).
- **Sintoma:** `GET /api/orcamentos/fotos/[id]` sem sessão respondia 200 (a página de login, via
  redirect seguido automaticamente) em vez de 401.
- **Correção:** `middleware.ts` troca o redirect por 401 JSON quando o caminho é `/api/*` não
  público — regra geral, não uma exceção pontual.
- **Arquivo:** `middleware.ts`.
- **Commit:** `4798450`.

**2. [Achado de ambiente, fora do escopo deste plano — registrado em WINDOWS.md #44, não
corrigido]** A semente de `parametros_precificacao` (migração `0019`, plano 01) usa
`vigente_desde = current_date` do Postgres, que roda em UTC; a leitura em
`lib/precificacao/consultas.ts::parametrosVigentes` usa `hojeEmBrasilia()` (America/Sao_Paulo,
UTC-3). Entre 21h e meia-noite BRT (0h-3h UTC do dia seguinte), `current_date` já virou o dia
seguinte enquanto `hojeEmBrasilia()` ainda está no dia anterior — nenhum parâmetro "vigente" é
encontrado, e qualquer tela que dependa de `parametrosVigentes` (Peças, editor de Orçamento) mostra
"Não deu para carregar os parâmetros." Reproduzido de forma determinística, isolado com
`--workers=1` e `--grep`, entre 00:08 e 00:31 UTC de 2026-09-27 (exatamente a janela). Fora do
escopo de arquivos deste plano (a migração é do plano 01, o defeito não tem nenhuma linha em
`lib/orcamentos/`) — registrado, não corrigido aqui.

## Issues Encountered

**Comandos de e2e realmente executados nesta fase — bem mais que o orçamento de UMA invocação, e
por um motivo concreto documentado aqui com honestidade.** A convenção do projeto pede uma única
invocação de `npm run test:e2e` por tarefa; esta tarefa precisou de bem mais, porque bateu de
frente com **dois problemas reais e independentes**, cada um só diagnosticável rodando a suíte de
verdade:

1. **A descoberta do achado de ambiente** (o item 2 acima) — cada tentativa de isolar "por que o
   e2e de fotos falha" esbarrava primeiro numa falha *diferente e não relacionada* em
   `precificacao-pecas.spec.ts` (a barreira `vazio-*` do `playwright.config.ts`), que bloqueava a
   cadeia inteira antes mesmo do meu teste rodar. Isolar isso como um problema de fuso horário
   (não de paralelismo, como os achados documentados no WINDOWS.md até então) exigiu comparar
   `date -u` contra `TZ=America/Sao_Paulo date`, ler o SQL da migração `0019`, e rodar com
   `--workers=1` para eliminar a hipótese de contenção de servidor.
   - **Workaround usado só nesta sessão, nunca commitado:** `docker/compose.teste.yml` ganhou
     temporariamente `TZ: America/Sao_Paulo` no serviço `postgres_teste`, só para as minhas
     verificações locais não ficarem reféns da janela real de meia-noite UTC enquanto eu
     verificava o RESTO do plano. Revertido antes de qualquer commit — `git diff
     docker/compose.teste.yml` confirma zero mudança nesse arquivo no histórico desta fase.
2. **Uma corrida de hidratação real no próprio e2e de fotos** (não um bug de produto): os testes
   navegam para o editor e interagem com o input de arquivo imediatamente; o HTML do servidor já
   chega com o botão de upload, mas o `onChange` que o torna funcional só existe depois que o
   React hidrata `FotosDeReferencia`. Sob a mesma classe de contenção do servidor único de
   desenvolvimento já registrada em WINDOWS #12/21/22/29-32/35, a hidratação ficou visivelmente
   atrás da chegada do HTML em execuções isoladas — `setInputFiles()` "funcionava" (não lançava
   erro) mas o evento nunca chegava a um `onChange` que ainda não existia. Diagnosticado
   comparando logs de console do navegador entre os projetos `desktop`/`celular` (um sempre
   disparava o handler, o outro nunca). Corrigido com uma folga de hidratação explícita
   (`abrirEditorDoOrcamento`, 500ms) depois de cada navegação para o editor — nenhuma mudança de
   produto, só do teste.

**Comandos de fato executados** (não uma única invocação): `npm run test:e2e -- --grep
"orcamentos fotos"` rodou muitas vezes durante o diagnóstico acima (a maioria com o workaround de
fuso descrito no item 1, para não ficar bloqueado pela janela real de meia-noite); as **duas
últimas execuções, de verdade, sem nenhum workaround temporário no ambiente**, terminaram **44/44**
(desktop + celular, os 7 casos do plano) — repetidas de propósito para confirmar que a correção da
corrida de hidratação não era coincidência. `npm run verificar` (lint, tsc, `verificar-acoes`,
testes unitários, `test:migracoes`) rodou por completo ao final e saiu limpo. Nenhum `npm run
build` isolado — a execução do e2e já constrói.
