# Phase 04.5 Plan 06: O editor do orçamento — para quem, para quando, e quais peças Summary

**`lib/orcamentos/contas.ts::contasDoOrcamento` (puro, TDD) soma as linhas em inteiros sem nunca
deixar uma peça sem cálculo contaminar o total; as quatro ações de edição travam o orçamento
(`select ... for update`) e recusam fora de rascunho; o editor na tela deixa o dono escrever para
quem é o pedido, escolher peças de duas portas diferentes e ver o total mudar ao vivo — e fecha o
item que o plano 05 deixou em aberto: uma peça em uso não se apaga, provado de ponta a ponta.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug de teste, achado pelo próprio e2e] `getByRole(..., { name })` com o nome da
peça interpretava os colchetes de "[e2e] ..." como classe de regex**
- **Found during:** Tarefa 3, primeira invocação de `npm run test:e2e -- --grep "orcamentos
  editor|precificacao pecas"` — os casos (b) do novo `orcamentos-editor.spec.ts` e (h) do
  `precificacao-pecas.spec.ts` travaram em timeout de 30s esperando o botão da peça dentro do
  diálogo "Qual peça".
- **Issue:** `dialogoEscolher.getByRole("button", { name: new RegExp(nomeDaPeca) })` — o Playwright
  trata `name` como regex quando não é string; `new RegExp("[e2e] Caneca...")` interpreta `[e2e]`
  como uma CLASSE de caracteres (casa um único caractere entre e/2), nunca a substring literal. O
  seletor nunca encontrava o botão de verdade.
- **Fix:** trocado para `.getByRole("button").filter({ hasText: nomeDaPeca })` — `hasText` com
  STRING faz correspondência literal por substring, nunca interpreta colchete.
- **Files modified:** `tests/e2e/orcamentos-editor.spec.ts`, `tests/e2e/precificacao-pecas.spec.ts`
- **Verification:** segunda invocação do e2e — 60/60 (todos os specs da varredura filtrada).
- **Committed in:** `df3ae5b`

**2. [Rule 1 - Bug de teste] `.blur()` seguido de `waitForLoadState("load")` corre risco de
falso positivo quando a navegação final é para a MESMA URL**
- **Found during:** Tarefa 3, primeira invocação do e2e — o caso (a), só no projeto `celular`,
  falhou porque o campo "Vale por (dias)" mostrava "10" (o padrão) em vez de "20" depois de um
  `page.reload()` explícito no fim do teste.
- **Issue:** como a gravação bem-sucedida navega (`window.location.assign`) para a MESMA URL que já
  está na barra de endereço, `page.waitForLoadState("load")` chamado DEPOIS do `blur()` pode
  resolver contra o carregamento ANTERIOR (já satisfeito) em vez de esperar o NOVO — uma corrida
  que só aparece sob certas latências (por isso só no `celular`, não no `desktop`, nesta execução).
  `tests/e2e/precificacao-parametros.spec.ts` usa o mesmo padrão frágil, mas não quebrou aqui.
- **Fix:** `blurEEsperarNavegacao` — `Promise.all([page.waitForNavigation({waitUntil:"load"}),
  campo.blur()])` — o listener é armado ANTES do evento que dispara a navegação, eliminando a
  corrida por construção.
- **Files modified:** `tests/e2e/orcamentos-editor.spec.ts`
- **Verification:** segunda invocação do e2e — 60/60, incluindo os dois projetos do caso (a).
- **Committed in:** `df3ae5b`
