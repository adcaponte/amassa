# Phase 06.2: Code Review Report

## Summary

I reviewed the current `main` version of the Phase 06.2 (Fornecedores) source: the anexo upload and
download Route Handlers, the Server Actions, the pure modules, the migration `0028`, the middleware
matcher exception, the backup and restore scripts, and the Financeiro integration. I also reviewed
the two commits made after the merge: `dafa82e` (`fileTypeFromBuffer` over the first 4 MiB of the
temporary file) and `555f0c7` (D-06: the unique index is now on `nome_normalizado(nome) where ativo`).

**Mechanical checks run on `main`:**
- `npx tsc --noEmit`: exit 0.
- `eslint` on the phase directories: exit 0.
- `node scripts/verificar-acoes.mjs app lib`: "122 ação(ões) conferida(s), 0 violações".

I did not run any e2e tests and did not touch any server.

**Overall:** the security posture holds up.
- **Authorization:** every exported Server Action starts with `exigirUsuario()`. Both Route Handlers
  call it before reading the database or the request body.
- **Path traversal:** paths go only through `caminhoDoAnexo()`, and the regex is duplicated in the DB
  check.
- **File type:** it comes from the file signature, never from the name. CSV and markup are refused,
  and `nosniff` plus `attachment` are set for spreadsheets.
- **Header injection:** `Content-Disposition` strips control characters.
- **Photos:** always re-encoded with no EXIF.
- **Concurrency:** the `for share` / `for no key update` lock pairs are deadlock-free. Each path locks
  exactly one `fornecedores` row.
- **D-06:** the change is consistent across the migration, `schema.ts`, the `23505` mapping and the
  migration test.
- **`dafa82e`:** correct. The 4 MiB cap is safe because `file-type` 22 falls back to the
  directory-name heuristic on `EndOfStreamError`.

**Not found:** no BLOCKER-class defect, no missing `exigirUsuario()`, no hardcoded secret, and no
English text facing the user.

The two warnings are both about how failures reach the person at the atelier. A database outage is
reported as "your session ended". A missing or unauthorized anexo replaces the app tab with raw JSON.
Everything else is Info: hardening, stale comments, and small edge cases.

## Warnings

### WR-01: A database or auth failure during upload is reported as "Sua sessão terminou" and the chosen file is thrown away

**File:** `app/gestao/api/fornecedores/anexos/route.ts:128-133` (also `app/gestao/api/fornecedores/anexos/[id]/route.ts:53-57`; client side in `components/amassa/cadastros/fornecedores/folha-anexo.tsx:278-283`)

**Issue:** `try { usuario = await exigirUsuario(); } catch { return recusar(401, FRASE_SESSAO_TERMINOU); }`
catches **every** error, not only the `NEXT_REDIRECT` that `exigirUsuario()` throws when there is no
session. `exigirUsuario()` also runs a `select` on `usuarios`. If Postgres is briefly unavailable, or
`auth()` throws, the PUT answers 401. The sheet then:
- clears the selected file and the preview (`setArquivo(null)`);
- tells the person their session ended and offers "Entrar de novo".

That instruction is wrong: the login would fail too. The person has to pick the 15 MB PDF again for
nothing. This breaks the "erro em linguagem humana, dizendo o que fazer" rule, because the message
names the wrong cause and the wrong action. Since this route sits outside the middleware (D-08),
nothing upstream catches the infrastructure error first. The GET route has the same pattern, which
it inherited from the orçamento photo route.

**Fix:** treat only the redirect as "no session" and let every other error become the generic 500:
```ts
import { isRedirectError } from "next/dist/client/components/redirect-error";

let usuario: UsuarioAutorizado;
try {
  usuario = await exigirUsuario();
} catch (erro) {
  if (isRedirectError(erro)) {
    return recusar(401, FRASE_SESSAO_TERMINOU);
  }
  console.error("Falha ao conferir a sessão no envio de anexo:", erro);
  return recusar(500, FRASE_FALHA_AO_ENVIAR);
}
```
If the internal import is unwanted, check `(erro as { digest?: string }).digest?.startsWith("NEXT_REDIRECT")`.

### WR-02: "Baixar" and "abrir" on a missing or unauthorized anexo replace the app tab with raw JSON

**File:** `components/amassa/cadastros/fornecedores/anexos-fornecedor.tsx:241-244`, `components/amassa/cadastros/fornecedores/tabela-vigente.tsx:93-102`, `app/gestao/api/fornecedores/anexos/[id]/route.ts:60-85`

**Issue:** the anexo links are plain `<a href="/gestao/api/fornecedores/anexos/<id>">`. When the file
exists, `Content-Disposition: attachment` makes the spreadsheet download without leaving the page.
On every error path the route answers JSON instead:
- `FRASE_ARQUIVO_SUMIU` (404 after a partial restore, or after the anexo was removed in another tab);
- `FRASE_ANEXO_NAO_ENCONTRADO`;
- the 401 from the middleware;
- the 500.

For a spreadsheet the "Baixar" anchor has no `target` and no `download`, so the browser **navigates
the app tab itself** to a page showing `{"erro":"O arquivo não está mais lá…"}`. The person loses the
ficha and sees raw JSON. For PDF and photo the same JSON opens in a new tab.

The phase planned for this case explicitly ("a restauração parcial do backup — isso é um 404 com
frase própria"), but the phrase never reaches the person in readable form. That conflicts with the
"Mensagens" and "Estados" constraints.

**Fix:** pick one of these.
- **(a)** Add the `download` attribute to the spreadsheet anchors. On a non-2xx answer the browser
  then reports a failed download instead of navigating.
- **(b)** Better: when the request is a navigation (`Sec-Fetch-Mode: navigate` or `Accept` includes
  `text/html`), have the GET answer a redirect back to the ficha with a notice. For example
  `NextResponse.redirect(new URL(\`/gestao/cadastros?sub=fornecedores&fornecedor=…&aviso=anexo-sumiu\`, request.url))`.
  The existing `AvisoCadastros` toast then shows the human phrase. Keep JSON for `fetch`.

## Info

### IN-01: The comment about how much `file-type` reads is stale after `dafa82e`

**File:** `app/gestao/api/fornecedores/anexos/route.ts:16` and `:221-222`
**Issue:** the header still says "`file-type` sobre o temporário gravado", and step 7 still says
"o `file-type` lê o quanto precisar". The next lines cap the read at 4 MiB with `fileTypeFromBuffer`,
so both comments contradict the code.
**Fix:** reword both to "os primeiros 4 MiB do temporário". Keep the explanation of why the cap is safe
(see IN-02).

### IN-02: With the 4 MiB cap, a large zip is accepted as XLSX by directory name alone (A-04 is weakened)

**File:** `app/gestao/api/fornecedores/anexos/route.ts:94, 229`; `lib/fornecedores/arquivo.ts:145-154`
**Issue:** in `file-type` 22, `detectZip` handles a truncated buffer specially. When it hits
`EndOfStreamError` before seeing `[Content_Types].xml`, it guesses from directory names, so any
`xl/…` entry yields `xlsx`. A zip larger than 4 MiB with an `xl/` folder and the manifest at the end
is therefore classified as a spreadsheet. So is an `.xlsm` with its manifest after 4 MiB, which
openpyxl-style writers produce. A-04 asked for exactly the opposite: "conferir `[Content_Types].xml`
para não aceitar qualquer zip". The impact is low, because the file is served as `attachment` with
`nosniff`.
**Fix:** accept it and record it in the A-04 note, or read the zip central directory (at the end of
the file) to confirm the content type when the file is larger than `BYTES_PARA_DETECTAR`.

### IN-03: `lerAmostra` duplicates `lerInicio` and reads the file a second time

**File:** `app/gestao/api/fornecedores/anexos/route.ts:96-116, 229-230`
**Issue:** the two functions are identical except for the length. The sample is just the first 8 KiB
of the buffer that `lerInicio` has already read.
**Fix:** `const inicio = await lerInicio(temporario, BYTES_PARA_DETECTAR); const amostra = inicio.subarray(0, TAMANHO_DA_AMOSTRA);` and delete `lerAmostra`.

### IN-04: The size check by `Content-Length` always uses the document phrase, even for a photo

**File:** `app/gestao/api/fornecedores/anexos/route.ts:155-162`
**Issue:** a photo with no extension above 20 MiB gets "…O limite é 20 MB para PDF e planilha"
instead of the 10 MB photo limit. The client normally stops a photo above 10 MB earlier, but only by
extension.
**Fix:** when `familiaPelaExtensao(meta.extensao) === "foto"`, use `fraseTamanhoDeFoto`. Otherwise
keep the current phrase.

### IN-05: Some legitimate CSV and PDF files are refused by the signature check

**File:** `lib/fornecedores/arquivo.ts:141-167`
**Issue:** `file-type` 22 matches 2-byte ASCII signatures before giving up. A CSV whose first bytes
are `BM` (bmp) or `MZ` (exe) gets a signature, so the CSV branch never runs and the file is refused
with 415. A PDF with bytes before `%PDF` (some ERP and scanner exports, which readers accept) is
refused too. Both are rare.
**Fix:** for the CSV case, when `extensao === "csv"` and `detectado?.ext` is one of the 2-byte ASCII
matches (`bmp`, `exe`), fall through to the text rule. Otherwise document the limitation.

### IN-06: Decoding a photo has no pixel cap (authenticated memory exhaustion)

**File:** `lib/fornecedores/foto.ts:36`
**Issue:** `sharp()` uses its default `limitInputPixels` of about 268 megapixels. A 10 MB PNG can
declare up to 16k×16k pixels, and decoding it before the resize can exhaust the container's memory
and take the app down for everyone. Only logged-in managers can upload, so the risk is low.
**Fix:** `sharp(bytesRecebidos, { limitInputPixels: 100_000_000 })`. That is above the 48 MP of an
iPhone photo. Anything larger becomes `FotoQueNaoAbre` and gets a 415.

### IN-07: `restaurar.sh` creates the anexos folder as the restoring user, never as uid 100

**File:** `scripts/restaurar.sh:176-177`
**Issue:** on a fresh server, `mkdir -p` creates the folder as the person running the script (root
or theo), and rclone writes the files with that same owner. The app runs as uid 100. It can read the
files but cannot create or unlink them. After that, every upload returns 500, and every "tirar"
leaves an orphan file behind with only a log line. The photo block has the same pattern, and
Roteiro 19 does not cover the post-restore case.
**Fix:** after a successful copy, print the exact commands
`sudo chown -R 100:101 "$BACKUP_ANEXOS_DIR" && sudo chmod 755 "$BACKUP_ANEXOS_DIR"`, or run them when
the script is root. Mirror the same change in the photo block.

### IN-08: `rclone copy` keeps removed anexos and `.envio-*` temporary files in the external copy forever

**File:** `scripts/backup.sh:262-275`; `scripts/restaurar.sh:177`
**Issue:**
- An anexo removed with "Tirar" leaves the server, as the confirmation says, but stays in the
  external copy indefinitely. A restore brings it back as an orphan file with no database row.
- `.envio-*` temporary files caught in mid-upload are copied and never cleaned up.
- `ANEXOS_HA_ARQUIVOS` counts `.envio-*` files while `ANEXOS_BYTES` excludes them.

**Fix:** add `--exclude '.envio-*'` to the anexos send. Decide deliberately between `copy` and `sync`
(or `copy` with a periodic `rclone cleanup`/retention) and write the decision in Roteiro 19.

### IN-09: The public `/api/health/backup` can echo the new anexos message, which contains the host path

**File:** `lib/backup/frescor.ts:81`; `scripts/backup.sh` (the `MENSAGEM_ERRO` of the unreadable-folder and failed-send branches for anexos)
**Issue:** when a run is recorded with `sucesso = false` (the `ao_sair` path), the `motivo` of the
public route adds `mensagem` verbatim. The anexos messages now include `/opt/amassa/dados/anexos-fornecedores`
and rclone's stderr, which can name the remote. That contradicts the T-06.2-34 comment added to
`app/api/health/backup/route.ts` ("nunca caminho de arquivo, nome do destino externo"). It is rare,
because the anexos step runs right before the success record. The behavior predates this phase.
**Fix:** do not echo `mensagem` on the public route. Keep the fixed `motivoBase`; the full message
stays in the database for the owner.

### IN-10: Small inconsistencies in the Financeiro link

**File:** `lib/fornecedores/acoes.ts:104`; `components/amassa/financeiro/painel-despesa.tsx:176-179, 205-208`; `lib/fornecedores/textos.ts:60-61`
**Issue:**
- (a) `criarFornecedor` revalidates only `/cadastros`, while edit, deactivate and reactivate also
  revalidate `/financeiro`. It works today only because the Financeiro page is dynamic.
- (b) A draft restored with a `fornecedorId` that is still active keeps the old `pessoa` text. If the
  supplier was renamed meanwhile, the field shows the old name as "ligado", while the server records
  the current name.
- (c) Since D-06 changed, `FRASE_NOME_REPETIDO` ("Já existe um fornecedor ativo com esse nome") also
  appears for names that differ only in accent or case ("Argila Goias" vs "Argila Goiás"), and the
  phrase does not say why.

**Fix:**
- (a) call `revalidarTelasDoFornecedor()` in `criarFornecedor` as well.
- (b) when restoring a valid link, replace the text with the current `fornecedores.find(f => f.id === id)?.nome`.
- (c) consider "Já existe um fornecedor ativo com esse nome (sem contar acento nem maiúsculas)…".
