## Warnings

### WR-01: A house order whose ficha later becomes "exclusiva" can never be concluded, and the error says it has no ficha

**Files:**

- `lib/producao/acoes.ts:1072-1104` (the conclusion decision)
- `lib/producao/consultas.ts:897-903` (how the item is found)
- `lib/precificacao/acoes.ts:320-333` (marking a ficha exclusive)

**Issue:** D-05 lets a casa order use a ficha "de linha". The piece row stores only `ficha_id`
(`item_catalogo_id` stays null, `acoes.ts:675-676`). At conclusion, the item comes from
`coalesce(ficha.item_catalogo_id, ordem_pecas.item_catalogo_id)`.

If someone marks that ficha "exclusiva" in Precificação while the order is running, `editarFicha`
sets `item_catalogo_id = null`. Then:

1. `peca.item` is `null`.
2. The D-12 promotion branch only runs for `ordem.tipo === "encomenda"` (line 1082), so for casa
   `promocao` stays `null`.
3. For casa, `destino` is forced to `"estoque"`, so `paraEstoque = boas > 0`.
4. Line 1101 rejects with `FRASE_SEM_FICHA_NAO_ENTRA_NO_ESTOQUE`: "Esta peça não tem ficha…". That
   is false: the piece does have a ficha.

A casa order has no "sem destino" option, so the only ways out are declaring every piece lost or
cancelling the order. If the owner flips the ficha back to "de linha", `promoverFichaParaLinha`
sees `item_catalogo_id = null` and creates a brand-new item. The original stock item is orphaned
and the pieces land in a duplicate.

**Scenario:** A casa order "Reposição de canecas" (linha ficha "Caneca cônica", item "Caneca
cônica" in stock) reaches Entrega. Meanwhile someone edits the ficha and ticks "exclusiva". At
"Guardar no estoque" every attempt fails with a message that contradicts the screen.

**Fix:** For casa orders, treat an exclusive ficha like the encomenda case: require the D-12 step
(`promocao`) and recarregar when it is missing. Alternatively, pin the item at creation: store
`item_catalogo_id = ficha.item_catalogo_id` in `conferirPecas`/`criarOrdem` for casa ficha pieces,
so the coalesce still finds the original stock item. Also give this case its own message instead
of reusing the "sem ficha" text.

```ts
// criarOrdem, casa + ficha de linha: pin the stock item the order will fill
itemCatalogoId: peca.origem === "item" ? peca.itemCatalogoId
  : (ehCasa && peca.origem === "ficha" ? fichas.get(peca.fichaId)!.itemCatalogoId : null),
```

### WR-02: Orders from an orçamento with more than 50 lines can never be concluded

**Files:**

- `lib/producao/esquemas.ts:161, 530-553`
- `lib/producao/gravacao.ts:144-156`
- `db/migrations/0024_producao.sql:158-166`

**Issue:** `esquemaConcluirOrdem.pecas` has `.max(LIMITE_DE_PECAS_POR_ORDEM)` (50). The code
comments call 50 a technical cap for the hand-made "Nova ordem". But two paths create orders with
no cap:

- `criarOrdemDoOrcamento` inserts one piece per orçamento line.
- The D-02 block (c) of 0024 does the same.

No limit on orçamento lines exists (grep over `lib/orcamentos` finds none). `concluirOrdem` also
requires every piece to be sent (`enviadas.size !== pecas.length`, line 1044). So an order with 51
or more pieces fails Zod on every attempt, with `FRASE_FALHA_AO_CONCLUIR` ("…verifique a internet
e tente de novo"), which is misleading.

**Scenario:** A café's full tableware quote with 60 SKU/colour lines is approved and produced. The
order sits in Entrega forever.

**Fix:** Cap conclusion at a limit that covers every source. For example, raise the conclusion
cap well above the orçamento maximum, or add a matching cap on orçamento lines. Or split the
limits: keep 50 for `esquemaCriarOrdem` and use a higher `LIMITE_DE_PECAS_NA_CONCLUSAO` (e.g.
1000) in `esquemaConcluirOrdem`. Either way, the rejection needs a real message instead of the
network-failure text.

### WR-03: House production can post "pieces" into the stock of a material counted in kg, g or ml

**Files:**

- `lib/producao/consultas.ts:595-610` (the picker list)
- `lib/producao/acoes.ts:764-774` (`conferirPecas`, item branch)
- `lib/producao/acoes.ts:1189-1215` (D-13 switch-on and the stock entry)
- `lib/producao/textos.ts:865-867`

**Issue:** The "Itens do estoque" group of the casa picker lists every active item that tracks
stock and is not tied to a ficha. That is exactly the raw materials and supplies: argila (kg),
esmalte (g), embalagens, café. `conferirPecas` checks only `controlaEstoque && ativo`, never the
unit.

At conclusion the entry is `milesimos: paraEstoque * 1000`, i.e. "one piece = one unit of the
item", in whatever unit the item already has. The D-13 switch-on keeps any existing unit through
`coalesce(unidade, 'un')`. The copy then tells the user "em unidades", which is not always true.

**Scenario:** Someone creates a casa order, picks "Argila vermelha" (kg) by mistake, makes 10 and
concludes with a typed cost of R$ 30 each. Estoque gets +10 kg of argila at R$ 300. That moves
the moving-average cost of the real clay and every later "consumo em encomenda" valued from it.

**Fix:** Restrict the casa item path to count-based items (`unidade = 'un'`, or `unidade is null`
for D-13) in three places:

- the picker query;
- `conferirPecas`, rejecting with a phrase;
- under the item lock in `concluirOrdem`, rejecting when `item.unidade !== null && item.unidade !== "un"`.

```ts
// listarCatalogoDaNovaOrdem.itensDoEstoque
and(eq(itensCatalogo.controlaEstoque, true), eq(itensCatalogo.ativo, true),
    eq(itensCatalogo.unidade, "un"), notExists(...))
```

### WR-04: The Estoque sheet's "order still running?" check does not serialize with cancelling or concluding the order

**Files:**

- `lib/estoque/gravacao.ts:446-461` (`encomendaEmAndamento`, `for key share`)
- `lib/estoque/acoes.ts:183-224` (it locks the item first)
- `lib/producao/acoes.ts:551-563` and `1022-1250` (the order-status writers)

**Issue:** `encomendaEmAndamento` filters `status in ('aguardando_sinal','ativa')` under
`FOR KEY SHARE`. `cancelarOrdem`, `concluirOrdem` and `cancelarOrdemDaVendaCancelada` change
`status` (a non-key column) while holding `FOR NO KEY UPDATE`. The two lock modes do not conflict,
so the Estoque transaction neither waits nor re-checks. It reads the pre-update row, finds
"ativa", and inserts a baixa linked to an order that commits as `cancelada`/`concluida` a moment
later.

The code comments claim the check is guaranteed (T-06.1-09), and the comment on
`lib/producao/gravacao.ts:17-22` states a global lock order DOCUMENTO → ORDEM → ITENS. The Estoque
sheet actually runs ITEM → ORDEM. The mode choice avoids the deadlock, but it also removes the
check it was meant to guarantee.

**Scenario:** Two phones: one taps "Cancelar ordem", the other registers "Consumo em encomenda →
esta ordem" in Estoque at the same moment. Both succeed. The ledger ends up with a consumption
linked to a cancelled order, and the cancel dialog's "N baixas" count was already wrong when
shown.

**Fix:** Follow the documented order in `registrarMovimentacao`. When `encomendaId` is present,
lock the order with `travarOrdem` (`for no key update`) and check its status before
`travarItens`. That is the same ORDEM → ITENS order `darBaixaNaOrdem` and `concluirOrdem` use, so
no new deadlock cycle appears. `encomendaEmAndamento` can then stay as the key-share reader for
the FK.

### WR-101: "Baixa total" can record the same missing clay/glaze twice (two phones, or a screen that has not refreshed)

**File:** `components/amassa/producao/folha-baixa.tsx:130-135, 197-202`; `components/amassa/producao/bloco-material.tsx:186-195`; server side `lib/producao/acoes.ts:832-899`
**Issue:** The "Baixa total" amount is worked out on the client from `pedido.baixadoMg`, which is a
snapshot taken when the page last rendered. `darBaixaNaOrdem` only receives an amount, so the
server has no way to see that the "total" is already booked. It records one more "consumo em
encomenda" every time.
**Failure scenario:** Clay for the order: 10 kg planned, 0 kg booked. Phone A taps "Baixa total"
and "Dar baixa", and 10 kg leave stock. Phone B opened the order before that, so it still says
"faltam 10 kg" and "Baixa total" is still enabled. B taps "Baixa total" and 10 kg more leave. The
Estoque now shows 20 kg of clay used, and the stock value (custo médio) drops for the second time.
Nobody is warned, and the only fix is a manual adjustment in the Estoque, because movements cannot
be edited (EST-06). One phone can hit the same thing if the refresh after the first baixa never
lands (see WR-106).
**Fix:** Send what the client believed was already booked for the "total" mode, and refuse under the
order lock if it has changed:
```ts
// folha-baixa.tsx
await darBaixaNaOrdem({
  ordemId, itemId: saldo.id, quantidadeTexto, material: pedido.material,
  baixadoEsperadoMg: pedido.modo === "total" ? pedido.baixadoMg : null,
});
// acoes.ts, inside the transaction after travarOrdem: recompute baixado for `material`;
// if (dados.baixadoEsperadoMg !== null && atual !== dados.baixadoEsperadoMg)
//   throw new RecusaDaProducao("Outra baixa de argila foi registrada enquanto você preenchia. A tela foi atualizada — confira o que falta.");
```

### WR-102: "Tentar de novo" on every new error screen does not fetch again: it calls `reset`, not `retry`

**File:** `app/gestao/(app)/producao/error.tsx:32`, `producao/[id]/error.tsx:32`, `producao/concluidas/error.tsx:33`, `producao/imprimir/error.tsx:27`, `producao/[id]/imprimir/error.tsx:27`
**Issue:** In Next 16.3.5, `ErrorBoundaryHandler.reset` only runs `setState({ error: null })`. The
boundary now also passes a `retry` prop, which does `startTransition(() => { router.refresh(); reset() })`
(`node_modules/next/dist/client/components/error-boundary.js:39-47,112-114`). These pages fail on the
server: a DB query throws, and the copy says "Verifique a internet e tente de novo". Calling `reset()`
redraws the same cached RSC payload, which still holds the error, so the error screen comes straight
back. The only recovery is a manual reload, which is awkward on a phone in standalone mode.
**Failure scenario:** The phone's network drops while the Produção page loads. The error screen
appears. Wi-Fi comes back and the user taps "Tentar de novo". The same error screen reappears, and
it keeps doing so however many times they tap.
**Fix:** Use the `retry` prop, or do the refresh by hand:
```tsx
export default function ErroProducao({ error, retry }: { error: Error & { digest?: string }; retry: () => void }) {
  ...
  <Button onClick={() => retry()}>...</Button>
}
// or: const router = useRouter(); onClick={() => startTransition(() => { router.refresh(); reset(); })}
```
(The error pages of Estoque, Financeiro and Queimas follow the same pattern and have the same
defect. That code is outside this phase, but the fix is the same.)

### WR-103: The 1-second guard on "Terminei" runs out before the new screen arrives, so the old button works again and shows a misleading refusal

**File:** `components/amassa/producao/botao-terminei.tsx:56-62, 80-82, 91, 101`
**Issue:** After a successful mark, the code sets `esperando = true` and starts a 1000 ms timer.
The comment says: "Até a tela trazer a etapa nova, o botão velho não aceita toque" ("until the screen
brings the new stage, the old button takes no taps"). That is not what the code does. The guard is
a fixed 1000 ms and ignores whether `router.refresh()` has landed. On a slow phone (3G in the
ateliê), or when the refresh does not commit (WR-106), the old label "Terminei: Secagem" becomes
tappable again after 1 s.
**Failure scenario:** The user taps "Terminei: Secagem" and the toast says "Feito: Secagem. Agora:
Queima de biscoito." The button still reads "Terminei: Secagem", so they tap again. The server
refuses: "Essa etapa já tinha sido marcada — talvez em outro celular. A tela foi atualizada." No
other phone was involved, and the screen may not have updated. Nothing is double-marked, because
`etapaEsperada` protects it, but the Valor-central flow now shows a false and alarming message.
**Fix:** Keep the button locked until the `etapa` prop actually changes, and start the 1 s window
only then:
```ts
const [aguardandoTela, setAguardandoTela] = useState(false);
if (etapaVista !== etapa) { setEtapaVista(etapa); setAguardandoTela(false); setEsperando(true); setInicioDaEspera(n => n + 1); }
// on success: setAguardandoTela(true) instead of starting the timer
disabled={gravando || esperando || aguardandoTela}
```
Add a longer fallback timeout, for example 10 s, that calls `router.refresh()` again and then
unlocks the button.

### WR-104: Refusal and error messages disappear when the refresh unmounts the component that shows them

**File:**
- `components/amassa/producao/acoes-da-ordem.tsx:70-83`: `BotaoTerminei` is replaced by the "Entreguei" button.
- `app/gestao/(app)/producao/[id]/page.tsx:224`: `AcoesDaOrdem` is only rendered while the order is `ativa`.
- `components/amassa/producao/trilha-etapas.tsx:97-98, 143-164`: `AjusteDias` is only rendered while the stage can be adjusted, and `CampoParcial` is keyed by stage.

**Issue:** `CaixaAguardando`, `ConfirmarCancelarOrdem` and `AvisoVendaCancelada` were written to stay
mounted after a `router.refresh()` so that a refusal ("already done on another phone") stays on
screen. The other controls do not do this. They keep their `erro` in local state, show the
refusal, call `router.refresh()`, and the new server state removes the component, taking the
message with it.
**Failure scenarios:**
- **"Terminei" just before Entrega.** Phone A shows "Terminei: Queima de esmalte". Phone B marks
  that stage. A taps and gets "Essa etapa já tinha sido marcada…". The refresh moves the order to
  Entrega, so `etapaParaTerminar` becomes `null` and `BotaoTerminei` unmounts. A only sees the
  button change to "Entreguei", with no explanation.
- **−/+ on a stage that just started.** Phone B marks Secagem. Phone A taps "+" on "Queima de
  biscoito", which is still in the future on A's old screen. The server refuses because that stage
  is now the current one. The refresh makes it the current stage in A's trail, `ajustavel` becomes
  false and `AjusteDias` unmounts. The tap is silently lost and the planned days stay the same.
- **"Já passaram" field.** A types a partial count and B marks the stage at the same moment. The
  save is refused, and the field (keyed by stage) unmounts together with the error and the number
  A typed.
- **Undo, or a mark, while the order is cancelled elsewhere.** If another phone cancels or finishes
  the order while the undo dialog or a refusal message is open, the whole `AcoesDaOrdem` unmounts.

**Fix:** Keep the last refusal in a component that does not depend on the order's state, and use
it for every action on the page. Examples: a small `AvisoDaOrdem` context/provider in `AcoesDaOrdem`'s
parent, or `toast.error(...)` for refusals whose target control may disappear. `FolhaConclusao`
already does the latter for `recarregar`, with the comment "a frase fica no toast, que sobrevive à
recarga".

### WR-105: "Fazer a mais" and "já passaram" never take the server's value after a refresh: they show the wrong number and skip real saves

**File:** `components/amassa/producao/campo-a-mais.tsx:31-33, 38`; `components/amassa/producao/campo-parcial.tsx:36-39, 44`
**Issue:** `texto` and `gravado` come from props only once, through `useState(String(aMais))`.
After a `router.refresh()` the `aMais`/`passaram` props change but the field does not. `salvar()`
then compares against the old `gravado` and skips the call when they match.
**Failure scenario:** Phone A opens an order with "a mais" = 0. Phone B sets it to 3. A taps any
action that refreshes the page, and the chip next to the piece now says "+3 a mais" while A's field
still says 0. A wants 0 extra pieces, types "0" and leaves the field. `"0" === gravado`, so nothing
is sent. The server keeps 3, the printed sheet says Fazer = pedido + 3, and A believes the extras
were cleared. The "já passaram" field has the same defect with `passaram`. The UI-SPEC only asks to
keep fields *while they are being edited*; it does not ask to keep a stale value forever.
**Fix:** Take the new server value whenever the field is not being edited, and always compare with
the latest server value:
```ts
const [focado, setFocado] = useState(false);
const doServidor = String(aMais);
const [ultimoDoServidor, setUltimoDoServidor] = useState(doServidor);
if (doServidor !== ultimoDoServidor) {
  setUltimoDoServidor(doServidor);
  setGravado(doServidor);
  if (!focado && !erro) setTexto(doServidor);
}
```

### WR-106: Every action calls `router.refresh()` right after a `revalidatePath`, which the project's own debug log shows makes the "screen never updates" race worse

**File:**
- The `router.refresh()` calls: `ajuste-dias.tsx:64`, `botao-terminei.tsx:91`, `caixa-aguardando.tsx:72`, `campo-a-mais.tsx:58`, `campo-parcial.tsx:69`, `confirmar-cancelar-ordem.tsx:103`, `confirmar-desfazer.tsx:79`, `folha-baixa.tsx:225`, `folha-conclusao.tsx:222`.
- The `router.push` after writing: `folha-nova-ordem.tsx:365-366`.

**Issue:** Every successful action in `lib/producao/acoes.ts` already calls `revalidatePath` for
`/gestao/producao/{id}` (lines 189-191, 248-250, 305-306, 326-329, 695-696, 896-898 and 1268-1271).
That makes the Server Action response carry the new RSC tree. The client then fires a second
`router.refresh()`.
- `.planning/debug/abertura-navegacao-trava.md` measured the silent DOM-commit failure after
  `ACTION_SERVER_ACTION` + `router.refresh()` at 63-70%. Removing the redundant refresh brought it
  down to 54% (62.7% → 53.9% over 102 attempts).
- The project's convention for writes elsewhere is a full navigation (`dialogo-aprovar.tsx:40-41,
  73-77`; `confirmar-apagar-peca.tsx:73-75`).
- `criarOrdem` goes the other way: it uses `router.push`, the call the same debug log found stalls
  in production builds.

**Failure scenario:** After "Terminei" or "Liberar", the toast confirms but the page never moves to
the new state. Combined with WR-103, the user keeps getting "already marked" refusals from a screen
that is stuck.
**Fix:**
- Drop `router.refresh()` from the success paths. The Server Action plus `revalidatePath` already
  refreshes the page.
- Keep `router.refresh()` only on the refusal and error paths, where the action returns before any
  `revalidatePath`.
- After `criarOrdem`, use `window.location.assign(rotaDeGestao(\`/producao/${id}\`))`, in line with
  the project's rule of a full navigation after writing.
- Add an e2e test that asserts the "Terminei" label changes within N seconds, in a production build.

### WR-107: While the catalogue is loading or has failed, "Criar ordem" can be tapped and does nothing visible

**File:** `components/amassa/producao/folha-nova-ordem.tsx:333-343, 446-485, 708`
**Issue:** The submit button is disabled only for `enviando || catalogoDaCasaVazio`. While
`catalogo.estado` is `"carregando"` or `"erro"`, the piece rows are not rendered: the form shows
the skeleton or the error block instead. `criar()` still runs `validarNovaOrdem`, which returns
`{ "peca-0": "Diga qual é a peça." }`. That key is in `ordemDosCampos()`, so `erroGeral` stays null.
The message belongs to a `LinhaPecaNovaOrdem` that is not mounted, and
`campos.current["peca-0"]` is null, so focus goes nowhere.
**Failure scenario:** On a slow connection the user types the name and taps "Criar ordem" before
the catalogue arrives, or after it failed. Nothing happens: no message and no focus change. The
error only shows up if the catalogue loads later. This breaks "erro em linguagem humana, dizendo o
que fazer".
**Fix:** Disable the submit button until the catalogue is ready, and point the button to the loading
or error text with `aria-describedby`:
```tsx
disabled={enviando || catalogoDaCasaVazio || catalogo.estado !== "pronto"}
```
Also, in `mostrarErros`, show a message in the footer for any error whose field is not rendered.

### IN-101: The fixed action bar has a fixed height, so a three-line "Terminei" label at 320px spills over the bottom navigation

**File:** `components/amassa/producao/barra-acao-fixa.tsx:26`; `components/amassa/producao/botao-terminei.tsx:100`

padding use the bar's real height (for example with a CSS variable set by a `ResizeObserver`), or
shorten the label on narrow screens.
