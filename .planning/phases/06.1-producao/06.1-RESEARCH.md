## Summary

A fase é, no banco, **três tabelas novas** (`ordens_producao`, `ordem_etapas`, `ordem_pecas`) que
substituem as três de Encomendas, **dois vínculos que já existem e mudam de alvo**
(`orcamentos.encomenda_id` e `movimentacoes_estoque.encomenda_id`, que passam a apontar para a
ordem), **uma coluna nova no livro do Estoque** (`material_da_ordem`, para saber o que era argila e
o que era esmalte na baixa) e **dois `check`s do livro relaxados** para aceitar a entrada de peça
pronta com origem `producao` ligada à ordem. No código, é trocar um módulo inteiro — `lib/encomendas/`
(10 arquivos), `components/amassa/encomendas/` (15), `app/gestao/(app)/encomendas/` (7), 8 testes
unitários, 7 specs e2e e 3 apoios de teste saem — e religar **seis pontos** de outros módulos:
`aprovarOrcamento`, `cancelarDocumento`, a folha de saída do Estoque, o bloco do Início, o veredito
do orçamento e o parâmetro "perda" em Cadastros.

A regra de negócio cabe inteira num módulo puro novo, `lib/producao/`, que recebe "hoje" e não lê
relógio: caminho → etapas, leitura da ordem (dias nesta etapa, previsão, selo), transições
(terminar, desfazer, ajustar previsto, liberar, parcial), fila do forno, material previsto,
conclusão (as cinco fórmulas do briefing §7, verbatim) e perda medida. Nada disso depende de
calendário "calculado para a frente": a situação passa a ser **lida das datas reais gravadas**, o
que elimina a cascata de `calcularCronograma` e os nove ramos de `situacaoEm`.

Os três riscos que mais podem derrubar a fase: (1) **ordem de publicação de uma migração
destrutiva** — o `insert` do Drizzle lista *todas* as colunas do esquema compilado
(`node_modules/drizzle-orm/pg-core/dialect.js:359-388`), então renomear ou apagar uma coluna que o
código antigo conhece quebra *todo* insert daquela tabela; e o código novo sem a migração quebra
todo cancelamento de venda (D-07). A saída é **expand/contract**: `0024` só acrescenta e religa
(código antigo continua rodando), `0025` apaga as tabelas velhas depois que o código novo está no
ar; (2) **impasse de travas** entre a baixa do Estoque (trava item → pede a ordem) e a conclusão
(trava ordem → pede item) — resolvido travando a ordem com `for no key update`, que não conflita
com o `for key share` da chave estrangeira; (3) **o `drizzle-kit generate` pergunta "criada ou
renomeada?"** quando o mesmo diff cria e apaga tabelas — um prompt interativo trava o executor. O
split `0024` (só cria) / `0025` (só apaga) evita isso também.

**Primary recommendation:** `lib/producao/` puro e testado primeiro (onda 0); depois a migração
`0024` aditiva (tabelas novas, vínculos religados, dado do D-02, `check`s do livro) com
`TABELAS_ESPERADAS` e uma prova em banco próprio; depois as telas; por último a `0025` (apaga
`encomendas*`) e o roteiro do dono na ordem **backup → publicar só a `0024` → aplicar → conferir →
publicar o código → `/api/health/producao` 200 → aplicar a `0025`**.

### Pergunta 5 — "Cabem" por peça, o parâmetro "perda" e onde mostrar a perda medida

- **Cabem:** não é coluna calculada — a ficha guarda medidas em mm e dois "já contei" anuláveis:

  (`queima2`); peça sem ficha (D-04) ou com `cabe: false` fica fora e é **contada** para a tela dizer
  "N peças sem estimativa".
- **O parâmetro "perda":** chave `perda_unica` do catálogo —
  `{ chave: "perda_unica", grupo: "Perda", rotulo: "Peças que se perdem no caminho", unidade: "%", escala: 100 }`

  (`lib/precificacao/consultas.ts:95`; `calculo.ts:118-123`, `custo = direto ÷ (1 − perda)`).
- **Onde mostrar a medida (D-08):** a tela do parâmetro é **Cadastros → Parâmetros**
  (`app/gestao/(app)/cadastros/page.tsx:124-127` → `components/amassa/cadastros/lista-parametros.tsx`),
  que desenha os grupos do catálogo em ordem (77-133) e já tem blocos extras por grupo
  (`grupo === "Trabalho"`, 103-114; `grupo === "No preço"`, 116-131). Acrescentar
  `grupo === "Perda"` com a linha de leitura "Perda medida nos últimos 6 meses: X% (N peças em M
  ordens)" — ou "Ainda sem medida: nenhuma ordem concluída nos últimos 6 meses". O número chega

- Observação: o "custo" que a entrada de peça pronta usa **já tem a perda embutida**

### Pattern 1: Decidir sob a trava da ordem, contra a etapa esperada
```typescript
// Source: molde de lib/estoque/acoes.ts:180-236 (tx + trava + decidir) — adaptado
const [ordem] = await tx
  .select({ id: ordensProducao.id, status: ordensProducao.status /* … */ })
  .from(ordensProducao)
  .where(eq(ordensProducao.id, dados.ordemId))
  .for("no key update"); // NUNCA "update": ver Pitfall 5
const etapas = await tx.select(/* … */).from(ordemEtapas)
  .where(eq(ordemEtapas.ordemId, dados.ordemId)).orderBy(asc(ordemEtapas.posicao));
const plano = planejarTerminar({ ...ordem, etapas }, dados.etapaEsperada, hoje); // puro
if (plano.tipo === "recusa") throw new RecusaDaProducao(plano.frase);
```

### Pattern 2: Escrita compartilhada fora de arquivo "use server"
`criarOrdemDoOrcamento`, `cancelarOrdemDaVendaCancelada`, `ordemParaVinculo` moram em
`lib/producao/gravacao.ts` **sem** a diretiva (Pattern 4 / Pitfall 7 da 06-RESEARCH): toda exportação
de arquivo `use server` vira endpoint e o `verificar-acoes` cobra `exigirUsuario()` nela.

### Pattern 3: A ordem nunca lê o relógio
`hojeEmBrasilia(new Date())` só na borda (página ou ação), exatamente como
`lib/orcamentos/acoes.ts:1118`. Todo `lib/producao/*.ts` puro recebe `hoje`.

### Anti-Patterns to Avoid
- **Deduzir a etapa da data:** o modelo novo só **lê** `feita_em`; qualquer cálculo "a etapa de hoje
  pelo calendário" é o modelo antigo voltando (PRD-12).
- **`for update` na ordem:** impasse com a folha do Estoque (Pitfall 5).
- **Apagar/renomear coluna que o código no ar conhece:** quebra todo `insert` daquela tabela (Pitfall 1).
- **Copiar arquivo de foto para a ordem:** as fotos são do orçamento (§3).
- **Custo ou preço na consulta da folha da ordem:** a defesa é não selecionar (PRD-19).
- **Segunda conta de "cabem" ou de custo:** use `quantasCabem` e `calcularPeca`.

## Common Pitfalls

### Pitfall 1: A janela entre migração destrutiva e código novo
**What goes wrong:** o `insert` do Drizzle lista **todas** as colunas do esquema compilado, usando
`default` para as ausentes (`node_modules/drizzle-orm/pg-core/dialect.js:359-388`, lido) — apagar ou
renomear `orcamentos.encomenda_id` ou `movimentacoes_estoque.encomenda_id` com o código antigo no ar
quebraria **toda criação de orçamento e toda venda/compra**. No sentido inverso, o código novo sem a
migração quebra **todo cancelamento de venda** (a D-07 consulta `ordens_producao`) e a aprovação.
**Why:** a migração é à mão; o pipeline só publica código; e a imagem `ferramentas` só nasce de `main`.
**How to avoid:** expand/contract (Pergunta 7). Com a `0024` aplicada e o código antigo no ar, o que
falha até o código novo subir: aprovar orçamento **com** a caixa da ordem marcada (a FK agora aponta
para as ordens — "nada foi criado", a frase genérica da D-25), e a baixa do Estoque com
"Qual encomenda?" preenchido. Venda, compra, cancelamento, orçamento, Estoque sem vínculo, Início:
funcionam. O roteiro diz isso ao dono e pede para não aprovar orçamento nesses minutos.
**Warning signs:** `git log origin/main..main` com código de `lib/producao` antes de
`/api/health/producao` responder 200.
*Com a D-09 (30/09/2026) o dono **aceita** essa janela — a plataforma ainda não é usada. Na ordem da
D-09 (código publicado, depois a migração) a janela é a do sentido inverso: código novo sobre o banco
velho, até o `db:migrate`. O roteiro a descreve e pede a migração logo depois do deploy.*

### Pitfall 2: A `0025` aplicada antes do código novo
**What goes wrong:** o código antigo lê `encomendas` em `obterOrcamentoParaEdicao`
(`lib/orcamentos/consultas.ts:170`, `leftJoin(encomendas…)`) — o editor de orçamento inteiro cai.
**How to avoid:** a `0025` é o **último** passo do roteiro, depois de `/api/health/producao` 200 **e**
de o dono abrir um orçamento aprovado no ar. `db:migrate` aplica "todas as pendentes": se a `0025`
já estiver na imagem no momento da `0024`, as duas vão juntas — por isso o commit só-migração leva
**só a `0024`**.
*Com a D-09 (30/09/2026) as duas vão juntas de propósito. O que continua valendo deste pitfall: a
migração só roda **depois** de o job `implantar` terminar (a imagem `ferramentas` é publicada antes
do `implantar`, então existe um intervalo em que ela já tem a `0025` e o código antigo ainda está no
ar).*

### Pitfall 3: `drizzle-kit generate` pergunta "criada ou renomeada?"
**What goes wrong:** quando o mesmo diff apaga uma tabela/enum e cria outro, o `drizzle-kit` pergunta
interativamente se é renomeação `[CITED: github.com/drizzle-team/drizzle-orm/issues/5307]` — o
executor fica parado num prompt. **How to avoid:** a `0024` é gerada com o `schema.ts` contendo as
tabelas **velhas e novas** (só cria); a `0025` depois de tirar as velhas (só apaga). A troca de alvo da
FK não pergunta nada (é `drop constraint` + `add constraint`). Conferir o SQL gerado antes de
acrescentar a parte à mão.

### Pitfall 4: Dado do D-02 lido fora de ordem
**What goes wrong:** anular `orcamentos.encomenda_id` **antes** de inserir as ordens apaga o vínculo
das que deveriam migrar; religar a FK antes do `update` falha com 23503 nas referências velhas.
**How to avoid:** ordem fixa: (a) ordens → (b) etapas → (c) peças → (d) anular o que sobrou →
(e) trocar as FKs → (f) `check`s do livro. Tudo na mesma transação do migrador.

### Pitfall 5: Impasse entre a baixa do Estoque e a conclusão
**What goes wrong:** a folha do Estoque trava o **item** (`travarItens`, `for no key update`) e depois
lê a ordem com `for key share` (`encomendaEmAndamento`, `lib/estoque/gravacao.ts:452`; a FK do
`insert` pede a mesma trava). A conclusão, se travar a **ordem** com `for update` e depois os itens,
fecha o ciclo: `FOR UPDATE` conflita com `FOR KEY SHARE`.
**How to avoid:** toda ação da Produção trava a ordem com **`for no key update`**, que **não** conflita
com `for key share` `[CITED: postgresql.org/docs/current/explicit-locking.html — "FOR NO KEY UPDATE … will not block SELECT FOR KEY SHARE"]`;
nenhuma ação da Produção trava documento. Ordem global: **documento → ordem → itens**. O `update`
da própria linha da ordem (sem mudar chave) já toma `FOR NO KEY UPDATE`.

### Pitfall 6: A extra boa "entra no Estoque" de um item que não controla estoque
**What goes wrong:** o item criado pela Precificação nasce `aparecenaVenda: true` e **sem**
`controla_estoque` (`lib/precificacao/acoes.ts:251-259`, `370-378`); `listarSaldos` só mostra itens
com `controla_estoque` — a movimentação seria gravada num item invisível no Estoque. E o check
`itens_catalogo_controla_exige_unidade_e_categoria_compra` (`db/schema.ts:641-644`) exige unidade e
categoria de compra para ligar. **How to avoid:** Open Question 3 — recomendação: a conclusão liga o
estoque do item na mesma transação (`unidade 'un'`, categoria de compra "Produção da casa", semeada
pela `0023`, `0023_estoque.sql:142-146`), e a tela diz que vai fazer isso.

### Pitfall 7: Duplo toque e duas pessoas no mesmo "Terminei"
**What goes wrong:** dois toques (ou dois celulares) marcam a etapa atual e depois a seguinte.
**How to avoid:** a ação recebe a **etapa esperada** ("Terminei: Secagem" manda `secagem`); sob a trava,
se a atual já não é essa, devolve "Essa etapa já foi marcada" sem gravar. Mesmo para "Desfazer" (manda
a etapa que vai desfazer) e para "Concluir" (status `ativa` sob a trava — senão entraria duas vezes no
Estoque).

### Pitfall 8: `passaram` sobrevivendo à etapa
**What goes wrong:** o parcial de "Secagem" aparece na "Queima de biscoito" e distorce a fila do forno.
**How to avoid:** `planejarTerminar` devolve `limparPassaram`; desfazer não restaura parcial (o
protótipo apaga, 341).

### Pitfall 9: Esmalte previsto no caminho "termina no biscoito"
**What goes wrong:** a ficha pode ter grama de esmalte; a ordem que para no biscoito mostraria
"Esmalte: faltam 1,6 kg" para sempre. **How to avoid:** `materialPrevisto(pecas, caminho)` zera o
esmalte quando `caminho === "biscoito"`; a folha da ordem idem.

### Pitfall 10: Unidade da baixa diferente de kg
**What goes wrong:** argila controlada em `g`, ou esmalte em `l`: somar milésimos crus mistura unidades.
**How to avoid:** `material.ts` converte por unidade do item (kg/g); `un/ml/l/m` ficam fora do "baixado
X de Y kg" com uma linha "N baixas em outras unidades"; a baixa total vem preenchida **na unidade do item**.

### Pitfall 11: Ficha apagada com ordem usando
`apagarFicha` só conta orçamentos (`lib/precificacao/acoes.ts:449-452`). Com a FK `ordem_pecas.ficha_id`,
apagar dá 23503 e a frase genérica. Estender a contagem e a frase ("usada em N ordens de produção").

### Pitfall 12: Afirmar os três números no e2e paralelo
São contagens do banco inteiro (Pergunta 12). Exatos só em `@vazio-historico` serial; nas paralelas,
afirmar o próprio cartão.

### Pitfall 13: `.next/types` velhos
Depois de apagar `app/gestao/(app)/encomendas`, o `tsc --noEmit` do `verificar` acusa TS2307 por
tipos gerados antigos — apagar `.next/types` e rodar de novo (nota do dono).

### Pitfall 14: O orçamento continua dizendo "ordem aberta" de uma ordem concluída/cancelada
`vereditoDaAprovacao` (`lib/orcamentos/situacao.ts:115-137`) compara com `"cancelada"`/`"concluida"`
do enum velho. Os status novos têm os mesmos dois valores terminais + `aguardando_sinal`/`ativa` —
"aberta" = um desses dois; reescrever os casos de `orcamentos-situacao.test.ts:72-110`.

export function derivarPeca(p: { tipo: "encomenda" | "casa"; pedido: number; aMais: number; perdidas: number }) {
  const feitas = p.pedido + p.aMais;
  if (!Number.isInteger(p.perdidas) || p.perdidas < 0 || p.perdidas > feitas) {
    return { ok: false as const, frase: `Diga um número de 0 a ${feitas}.` };
  }
  const boas = feitas - p.perdidas;
  if (p.tipo === "casa") {
    return { ok: true as const, feitas, boas, entregues: 0, extrasBoas: boas, faltam: 0 };
  }
  return {
    ok: true as const,
    feitas,
    boas,
    entregues: Math.min(p.pedido, boas),
    extrasBoas: Math.max(0, boas - p.pedido),
    faltam: Math.max(0, p.pedido - boas),
  };
}

### Known Threat Patterns for este stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cliente forja a etapa, a data real ou o custo da entrada | Tampering | Servidor decide a etapa atual lendo o banco; `feita_em = hoje` calculado na ação; custo por `calcularPeca` no servidor |
| Conclusão dupla (duas pessoas / duplo toque) gera duas entradas no Estoque | Tampering | Trava da ordem + `status = 'ativa'` conferido sob a trava |
| Função auxiliar com `tx` exportada de arquivo `use server` vira endpoint | Elevation of Privilege | `lib/producao/gravacao.ts` sem a diretiva; `verificar-acoes` barra |
| Ordem apagada some com o histórico de baixa | Repudiation | `revoke delete` + FK sem `on delete`; só "cancelar" |
| Folha da ordem vazando preço/custo para a bancada | Information Disclosure | A consulta da folha não seleciona dinheiro; teste "nenhum `R$`" |
| `/api/health/producao` revelando volume | Information Disclosure | Corpo só `{ status }` (molde `health/estoque`) |
| Migração destrutiva aplicada pela automação | Tampering / Availability | Só à mão, pelo dono, depois de backup; roteiro com contagem antes/depois; `0025` só depois do código |
| Texto livre de personalização na folha | Tampering (XSS) | React escapa; nenhum `dangerouslySetInnerHTML` |
| Mensagem do banco na tela | Information Disclosure | Frase humana; SQLSTATE só no log via `codigoDoErroPostgres` |
