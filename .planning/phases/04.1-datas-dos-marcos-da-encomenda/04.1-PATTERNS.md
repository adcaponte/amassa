## Pattern Assignments

### `lib/encomendas/cronograma.ts` (utility, transform) — THE central file

**Current exact shape to change:**

`DIAS_PADRAO` (lines 35-42), current values:
```typescript
export const DIAS_PADRAO: readonly DuracaoDeEtapa[] = [
  { etapa: "producao", dias: 3 },
  { etapa: "secagem", dias: 6 },
  { etapa: "queima1", dias: 1 },
  { etapa: "esmaltacao", dias: 1 },
  { etapa: "queima2", dias: 1 },
  { etapa: "entrega", dias: 1 },
];
```
Per D-04/D-05, target: producao 5, secagem 15 (durations unchanged in kind); the three marco
entries need a NEW field (the wait/espera before the marco), not just `dias`. Whatever shape
`DuracaoDeEtapa` becomes, `DIAS_PADRAO`'s marco entries carry espera 0 (biscoito), 3 (esmalte),
5 (entrega), per D-05 — separate from `dias` which per D-06 becomes fixed at 1 for all marcos
(marco "always happens, always 1 day").

`ETAPAS_MARCO` (line 28) and the marco-validation block inside `calcularCronograma` (lines
173-191) are the two places that currently enforce "marco dias ∈ {0,1}" — this whole concept
of a togglable marco needs to be rewritten per D-06/D-07: marco `dias` becomes fixed at 1
(no longer input), and a new numeric field (espera) becomes the thing that's validated as
`>= 0` integer, feeding a GAP before the marco's 1-day block (D-09: the gap is empty space,
not a drawn segment).

`FaixaDeEtapa` type (lines 57-68) and the cascade loop (lines 193-233) are where the espera
must be spliced in: `inicio`/`fimExclusivo` currently derive from cursor + `dias` only; the
gap needs to advance the cursor by espera BEFORE the marco's own 1-day block starts, without
being represented as its own faixa with `dias > 0` (per D-09, "não desenhar bloco tracejado
próprio" — the existing `desenhada: false` / cursor-skip pattern for `dias === 0` at lines
202-216 is the closest existing precedent for "advance the cursor without drawing a block").

**Module discipline to preserve (lines 1-11 comment block) — copy verbatim style:**
```typescript
// Módulo puro: recebe dados, devolve dados. Zero imports (regra de `lib/backup/frescor.ts` /
// 01-ARQUITETURA.md §3), e "hoje" nunca é lido do relógio por dentro — quando uma função
// precisar dele, ele entra como argumento. ...
```
Any new function/field added here must keep zero imports, no `Date`, "hoje" as argument only.

**Validation-throw pattern to replicate for the new espera field** (lines 177-191):
```typescript
for (const duracao of duracoes) {
  if (!Number.isInteger(duracao.dias) || duracao.dias < 0) {
    throw new RangeError(
      `A etapa "${duracao.etapa}" tem duração inválida (${duracao.dias}): precisa ser um ` +
        "número inteiro de dias maior ou igual a 0.",
    );
  }
  if (ETAPAS_MARCO.includes(duracao.etapa) && duracao.dias !== 0 && duracao.dias !== 1) {
    throw new RangeError(...);
  }
}
```
One `if` per case, no silent coercion — this is the pattern the new espera-range check should
follow (e.g. reject non-integer/negative espera the same way).

**`STATUS_DE_ENCOMENDA` duplication-of-truth pattern (lines 44-53)** — precedent for how this
module tolerates a second copy of an enum, kept in sync only by a test — same tolerance
applies if the new espera concept needs a name shared with `esquemas.ts`.

### `db/schema.ts` — `encomendaEtapas` (model, CRUD)

**Current exact DDL-equivalent (lines 169-193):**
```typescript
export const encomendaEtapas = pgTable(
  "encomenda_etapas",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    encomendaId: uuid("encomenda_id").notNull().references(() => encomendas.id, { onDelete: "cascade" }),
    etapa: etapaEncomenda("etapa").notNull(),
    dias: integer("dias").notNull().default(1),
    ordem: integer("ordem").notNull(),
    criadoEm: timestamp("criado_em", { withTimezone: true }).notNull().defaultNow(),
    atualizadoEm: timestamp("atualizado_em", { withTimezone: true }).notNull().defaultNow(),
  },
  (tabela) => [
    unique("encomenda_etapas_encomenda_etapa_uk").on(tabela.encomendaId, tabela.etapa),
    check(
      "marcos_zero_ou_um",
      sql`${tabela.etapa} not in ('queima1','queima2','entrega') or ${tabela.dias} in (0, 1)`,
    ),
    check("encomenda_etapas_dias_nao_negativo", sql`${tabela.dias} >= 0`),
    index("encomenda_etapas_encomenda_idx").on(tabela.encomendaId),
  ],
);
```
Per D-06/D-07/Discretion: `marcos_zero_ou_um` "deixa de fazer sentido como está". Options left
to Claude's discretion: either (a) rewrite it to `dias = 1` for marcos, or (b) drop it and add
a new check on the new espera column (e.g. `espera >= 0`, possibly with a marco-only
constraint mirroring the shape already used at lines 187-189). **Closest analog for a
column+check-constraint pair added at the same table** is `encomenda_itens` (lines 140-163)
which pairs `quantidade: integer(...).notNull()` with `check("encomenda_itens_quantidade_positiva", sql`${tabela.quantidade} > 0`)` — same one-column/one-check idiom to copy for the new
espera column and its non-negative (or marco-only) check.

**Comment convention to preserve** (line 165-168 — comment directly above the table explains
the constraint's reason) — the new espera column's rationale (D-01/D-06/D-07) belongs in the
same place, replacing the now-obsolete "para os três marcos ... só 0 ou 1 é válido" sentence.

### New Drizzle migration (no strong analog — see `No Analog Found`)

**Closest available analog**, `db/migrations/0005_encomendas.sql` — shows Drizzle's
CHECK-constraint DDL syntax to reuse verbatim, e.g.:

by copying a CREATE-shaped analog. D-10's guard (confirm `count(*)` is 0 in production before
applying) has no analog either — it is a manual runbook step, not code; document it in the
plan's rollout section, not as a code artifact.

export const esquemaEtapas = z

## Shared Patterns

### Pure-module discipline (zero imports, no `Date`, "hoje" as argument)
**Source:** `lib/encomendas/cronograma.ts` lines 1-11, `lib/encomendas/gantt.ts` lines 1-16,
`lib/encomendas/trilha.ts` lines 1-10
**Apply to:** any new code added inside these three files. Calendar arithmetic
(`diasDesdeAEpoca`/`civilDesdeDias`/`somarDias`/`diferencaEmDias`) is intentionally duplicated
across all three — do not attempt to deduplicate by adding an import.

### Server Action entry discipline
**Source:** `lib/encomendas/acoes.ts` line 43 (`const usuarioAtual = await exigirUsuario();` as
literal first statement of `criarEncomenda`), line 341 (same in `ajustarEtapaEncomenda`)
**Apply to:** any new/modified Server Action touching the espera field.

### Single point of validation (D-15)
**Source:** `lib/encomendas/esquemas.ts` (`esquemaEtapas`, `esquemaAjusteDeEtapa`), referenced
by both `criarEncomenda`/`atualizarEncomenda` and `ajustarEtapaEncomenda` in `acoes.ts`
**Apply to:** the espera field's validation must live in `esquemas.ts` only — never
reimplemented inside `acoes.ts` or a component.

### Optimistic passo 1-4 cycle (never truly optimistic on the final numeric confirm)
**Source:** `components/amassa/encomendas/ajuste-rapido-etapa.tsx` lines 30-38, 49-72
**Apply to:** whatever quick-adjust control replaces the marco `Switch`.

### `data-testid` naming convention
**Source:** `linha-marco-${etapa}` / `estado-marco-${etapa}` (formulario-encomenda.tsx),
`ajuste-switch-${etapa}` / `ajuste-rapido-${etapa}` / `ajuste-numero-${etapa}`
(ajuste-rapido-etapa.tsx), `gantt-marco-${encomenda.id}-${faixa.etapa}` (gantt.tsx)
**Apply to:** new test ids for the espera field/control — keep the `${etapa}`-suffixed
convention so Playwright selectors already scoped this way keep working where unchanged.
