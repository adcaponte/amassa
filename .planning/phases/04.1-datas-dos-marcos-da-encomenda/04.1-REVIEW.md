# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-22

## Summary

This re-review covers the whole of Phase 04.1 (plans 04.1-01 through 04.1-06), superseding the
prior report committed at `ed8ceaf`. The two prior BLOCKER-tier findings are confirmed **closed**,
with real regression coverage backing both fixes; one prior WARNING is confirmed **closed**; one
prior WARNING was **deliberately deferred** by the product owner and is carried forward unchanged;
one prior INFO item remains open, unchanged, and still low-risk.

**CR-01 (gap 16, cascade fed etapas without `ORDER BY ordem`) — CLOSED.** Both call sites in
`lib/encomendas/acoes.ts` (`concluirEncomenda:281-289`, `ajustarEtapaEncomenda:391-401`) now carry
`.orderBy(asc(encomendaEtapas.ordem))`, with the `.orderBy` placed before `.for("update")` as
required. The fix is backed by three independent layers of regression proof, which is unusually
thorough and worth noting as a strength: a structural AST-walking test
(`tests/unit/leituras-ordenadas.test.ts`) that fails if `orderBy` disappears from *any* read of
`encomenda_etapas` in `acoes.ts`/`consultas.ts`, paired with intentionally-wrong/right fixtures
(`tests/fixtures/leituras/{sem,com}-ordem.ts`) so the test's own gate is provable; and a real-Postgres
e2e test (`tests/e2e/encomendas-ordem-das-etapas.spec.ts`) that physically reorders tuples via
delete+reinsert and proves the cascade output differs without the ordering fix. This is exactly the
kind of proof a code review can't provide by inspection alone, and it's present here.

**CR-02 (gap 17, `AjusteInvalido` swallowed, spinner stuck) — CLOSED.** `lib/encomendas/acoes.ts`
now defines `class AjusteInvalido extends Error {}` (line 111), throws it instead of a plain `Error`
at the 365-day validation boundary (line 428), and the `catch` block in `ajustarEtapaEncomenda`
translates it to `{ ok: false, erro: erro.message }` (lines 456-462) without a `console.error` (a
deliberate choice, correctly commented, to keep expected-validation-failure noise out of the error
log). `components/amassa/encomendas/ajuste-rapido-etapa.tsx` wraps the call in `try/catch/finally`
with `setPendente(false)` in `finally` (lines 77-104), so the spinner can no longer get stuck on
this path or on any other thrown error. Backed by
`tests/e2e/encomendas-detalhe.spec.ts` ("o ajuste rápido recusa uma espera acima de 365..."), which
reproduces the exact two-session race from the original finding via `definirEsperaDaEtapa` writing
directly to the database, and asserts the Portuguese message reaches a toast and the control
re-enables.

**WR-01 (migration runbook's D-10 guard didn't check the invariant the migration introduces) —
CLOSED.** `docs/operacao/06-migracao-espera-dos-marcos.md` §1 now includes the exact
`dias <> 1` query against marker rows as a named second guard, with "pare aqui" language and an
explicit note that the migration has already been applied successfully (the doc has been corrected
for future readers, not describing a live incident).

**WR-03 (two conflicting completion dates in `TrilhaEtapas` after concluding) — carried forward,
still DEFERRED.** `components/amassa/encomendas/trilha-etapas.tsx:109-120` documents this at length
in its own comments and explicitly declines to fix it, on the stated grounds that disabling the six
`AjusteRapidoEtapa` controls post-conclusion is a product decision, not a defect fix. This review
does not re-raise it as new — the deferral is a legitimate, recorded decision — but the underlying
inconsistency (rodapé "Conclusão prevista" can update after conclusion while the situação line still
shows the original "Concluída em" date) remains real and user-visible if a manager touches a
quick-adjust control after concluding. No action requested; flagged here only so this REVIEW.md
carries the phase's full status forward.

**IN-01 (marker rows' `dias` field never registered by the form) — carried forward, still open.**
`components/amassa/encomendas/formulario-encomenda.tsx`'s `EtapaDoFormulario` (lines 362-416) still
only registers `etapas.${indice}.esperaDias` for marker rows; `dias` is never rendered or bound for
markers, relying entirely on the DB/Zod invariant to keep it at `1`. Confirmed still true against
current code and against `tests/e2e/encomendas-formulario.spec.ts` (only `campo-espera-*` is
exercised for markers, no `dias` input exists to test). Unchanged from the prior review — no new
risk introduced, still a "no action required now" item.

One new WARNING surfaced during this pass, unrelated to the two closed BLOCKERs: a stale test
comment that documents pre-Phase-04.1 default durations, which is misleading to a future reader
even though it does not affect actual test correctness (the test computes its expected values from
`DIAS_PADRAO` directly, never from the stale numbers in the comment).

## Warnings

### WR-04: Stale comment in `encomendas-filtros.spec.ts` documents pre-04.1 `DIAS_PADRAO` values

**File:** `tests/e2e/encomendas-filtros.spec.ts:60-61`

**Issue:** The comment above the `criarEncomenda` test helper reads:

```ts
// Cria pela Server Action real via formulário — nunca INSERT direto no banco. As 6 etapas nascem
// com `DIAS_PADRAO` (produção 3 · secagem 6 · queima1 1 · esmaltação 1 · queima2 1 · entrega 1).
```

But Phase 04.1 changed `DIAS_PADRAO` (`lib/encomendas/cronograma.ts:47-54`) to
`produção 5 · secagem 15 · queima1 1 (espera 0) · esmaltação 1 · queima2 1 (espera 3) · entrega 1
(espera 5)` — the comment still cites the pre-04.1 numbers (`3`/`6`) and omits the espera values
entirely. This is a documentation-only defect (the test logic itself imports `DIAS_PADRAO` and
`calcularCronograma` directly at lines 367-368 rather than hardcoding the stale numbers, so no test
assertion is actually wrong), but a future reader skimming this comment to understand what the
fixture produces will be misled about both the duration numbers and the existence of the espera
gaps this same spec file's Gantt-adjacent tests rely on elsewhere in the suite.

**Fix:**
```ts
// Cria pela Server Action real via formulário — nunca INSERT direto no banco. As 6 etapas nascem
// com `DIAS_PADRAO` da fase 04.1 (produção 5 · secagem 15 · queima1 1 (espera 0) · esmaltação 1 ·
// queima2 1 (espera 3 antes) · entrega 1 (espera 5 antes)).
```

## Info

### IN-01: Marker rows' `dias` field is never registered by the form — implicit trust with no client-side guard

**File:** `components/amassa/encomendas/formulario-encomenda.tsx:362-401`

**Issue:** (Carried forward from the prior review, unchanged.) `EtapaDoFormulario` only calls
`register(...)` on `etapas.${indice}.esperaDias` for marker rows — `etapas.${indice}.dias` is never
registered for the three markers, so its value travels through the form purely as whatever
`valoresIniciais()` seeded (`DIAS_PADRAO`'s `1` on create, or `linha.dias` from the database on
edit) with no UI path to see or correct it if it were ever wrong. This is safe today because the
DB/Zod invariant guarantees marker `dias === 1` at write time, so no bad value should ever reach
`valoresIniciais()` — but a future regression that puts a marker row at `dias !== 1` in the database
would silently round-trip through this form with no visual indication anything is wrong.

**Fix:** no action required now; if this module ever needs a defensive display, a
`disabled`/read-only rendering of `dias` for markers (e.g. "Sempre 1 dia") would make the invariant
visible instead of implicit.

### IN-02: `TrilhaEtapas` dual-date drift after conclusion — deliberately deferred, carried forward for status tracking

**File:** `components/amassa/encomendas/trilha-etapas.tsx:107-168`

**Issue:** (Carried forward from the prior review as WR-03; downgraded to Info here only to reflect
that it is a recorded, owner-approved deferral rather than an unaddressed defect — the underlying
behavior is unchanged.) `duracaoTotalEmDias`/`dataDeConclusao` in the footer are seeded once from
the `cronograma` prop via `useState` and only update when one of the six `AjusteRapidoEtapa`
controls confirms a server response. The situação line, by contrast, is recomputed from
`conclusaoConfirmada` once "Marcar como concluída" succeeds. Because the component never remounts
on `router.refresh()` (a documented, deliberate choice — see the component's own extensive comment
citing a measured 3-in-50 refresh-delivery failure rate), a manager who concludes an encomenda and
then still touches a quick-adjust control will see the footer's "Conclusão prevista" recompute to a
new date while the situação line above continues to show the original "Concluída em {date}" —
two conflicting dates on the same screen simultaneously.

**Fix:** Already proposed in the prior review and explicitly not actioned by design: once
`!podeConcluir`, render the six `AjusteRapidoEtapa` controls read-only, so the footer's derived
state can no longer drift from the situação line post-conclusion. This is a product-facing
behavior change the component's own comments say requires the owner's sign-off before
implementing — no further action expected from this review.
