# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-22T09:29:51Z
**Depth:** standard
**Files Reviewed:** 31 (listed above; some paths are directories of related spec/test files reviewed individually)
**Status:** issues_found

## Summary

This phase converts the three encomenda "marcos" (queima1, queima2, entrega) from an on/off
switch to an always-on, always-1-day milestone with a new `espera_dias` (wait-before) counter.
The three-layer invariant this depends on — DB check, Zod schema, and UI — is implemented
**consistently**: `marcos_sempre_um_dia`/`encomenda_etapas_espera_no_intervalo`/
`espera_so_em_marco` in `db/schema.ts` match `0009_espera-dos-marcos.sql` and
`meta/0009_snapshot.json` exactly, and `lib/encomendas/esquemas.ts` mirrors the same 0/365
bound and marker-only-espera rule that the database enforces. `lib/encomendas/cronograma.ts`
and `lib/encomendas/trilha.ts` are pure, well-tested, and correctly treat the wait as a cursor
advance that never becomes its own drawn faixa. `02-MODELO-DE-DADOS.md` was genuinely rewritten
to stop describing the old switch model. `exigirUsuario()` is the first statement in every
Server Action in `lib/encomendas/acoes.ts`.

Two real defects were found, both in `lib/encomendas/acoes.ts`, both introduced or touched by
this phase's changes:

1. Two of the SELECTs that feed `calcularCronograma()` (the cascade calculator, where order of
   input is load-bearing) do not `ORDER BY encomenda_etapas.ordem`, unlike every other etapas
   read path in the codebase (`lib/encomendas/consultas.ts` orders by `ordem` in all four of its
   queries). This risks a corrupted cascade under normal PostgreSQL semantics (no ORDER BY = no
   ordering guarantee), and one of the two call sites is the very function this phase modified
   to add per-row UPDATEs on markers (`ajustarEtapaEncomenda`), which increases the odds of
   physical row order drifting from `ordem` over an encomenda's lifetime.
2. The one validation failure path inside `ajustarEtapaEncomenda` that the code's own comments
   say should reach the user "com a mensagem em português" instead throws an uncaught `Error`
   that isn't converted to `{ ok: false }`, permanently freezing the quick-adjust widget's
   spinner on the client with no error shown.

Three warnings and one info item round out the review — an accessibility gap on the new
"espera" counter, a gap in the production migration runbook's pre-flight guard, a
self-documented (but still real) stale-state defect in `TrilhaEtapas`, and a minor
defense-in-depth gap in the form.

## Critical Issues

### CR-01: `calcularCronograma()` fed etapas without `ORDER BY ordem` — cascade can compute in the wrong sequence

**File:** `lib/encomendas/acoes.ts:268-277` (`concluirEncomenda`) and `lib/encomendas/acoes.ts:374-383` (`ajustarEtapaEncomenda`)

**Issue:** `calcularCronograma(dataInicio, duracoes)` explicitly documents that it "calcula a
cascata inteira" by walking `duracoes` **in the order it receives them** — it does not sort by
any `ordem` field. Every other place in the codebase that reads `encomenda_etapas` for this
purpose orders explicitly:

```
lib/encomendas/consultas.ts:40:   .orderBy(asc(encomendaEtapas.ordem)),   // listarEncomendasDoIndice/listarEncomendasAtivas
lib/encomendas/consultas.ts:118:  .orderBy(asc(encomendaEtapas.ordem)),   // buscarEncomenda
```

But the two SELECTs in `lib/encomendas/acoes.ts` that also feed `calcularCronograma()` have no
`.orderBy(...)` at all:

```ts
// concluirEncomenda, lib/encomendas/acoes.ts:268-275
const etapasDaEncomenda = await db
  .select({ etapa: encomendaEtapas.etapa, dias: encomendaEtapas.dias, esperaDias: encomendaEtapas.esperaDias })
  .from(encomendaEtapas)
  .where(eq(encomendaEtapas.encomendaId, id));           // <- no orderBy

// ajustarEtapaEncomenda, lib/encomendas/acoes.ts:374-383
const etapasAtuais = await tx
  .select({ id: ..., etapa: ..., dias: ..., esperaDias: ... })
  .from(encomendaEtapas)
  .where(eq(encomendaEtapas.encomendaId, entrada.encomendaId))
  .for("update");                                        // <- no orderBy
```

Without `ORDER BY`, PostgreSQL gives **no ordering guarantee** on the returned rows — this is
standard SQL semantics, not an edge case. In practice a sequential scan often returns rows close
to insertion order for an untouched table, but `ajustarEtapaEncomenda` itself issues a targeted
`UPDATE ... WHERE id = etapaAlvo.id` on every call (line 413-416), and repeated single-row
updates are exactly the kind of activity that can relocate a tuple's physical position over
time. If the six rows are ever returned out of `producao → secagem → queima1 → esmaltacao →
queima2 → entrega` order, `calcularCronograma` will build the cascade starting from whichever
etapa came first in the scan, producing a wrong `inicio`/`fimExclusivo` for every faixa and a
wrong `dataDeConclusao` — the exact "Conclusão prevista" value shown to the user right after a
quick-adjust or after clicking "Marcar como concluída". This directly undermines the phase's own
core deliverable (correct cascade dates around the new espera gaps).

**Fix:**
```ts
// concluirEncomenda
const etapasDaEncomenda = await db
  .select({ etapa: encomendaEtapas.etapa, dias: encomendaEtapas.dias, esperaDias: encomendaEtapas.esperaDias })
  .from(encomendaEtapas)
  .where(eq(encomendaEtapas.encomendaId, id))
  .orderBy(asc(encomendaEtapas.ordem));

// ajustarEtapaEncomenda
const etapasAtuais = await tx
  .select({ id: encomendaEtapas.id, etapa: encomendaEtapas.etapa, dias: encomendaEtapas.dias, esperaDias: encomendaEtapas.esperaDias })
  .from(encomendaEtapas)
  .where(eq(encomendaEtapas.encomendaId, entrada.encomendaId))
  .orderBy(asc(encomendaEtapas.ordem))
  .for("update");
```
`asc` is already imported in this file (`import { and, asc, eq, inArray } from "drizzle-orm"`),
so this is a one-line fix at each call site.

### CR-02: Unhandled validation failure freezes `AjusteRapidoEtapa` and discards the Portuguese error message

**File:** `lib/encomendas/acoes.ts:408-411` and `:434-440` (`ajustarEtapaEncomenda`); consumed by `components/amassa/encomendas/ajuste-rapido-etapa.tsx:53-84`

**Issue:** Inside the transaction, when the recomputed `esperaDias` (or `dias`) fails the shared
`esquemaEtapas` re-validation (e.g. incrementing `esperaDias` past 365), the code deliberately
throws a plain `Error` carrying a human, Portuguese message:

```ts
const validacao = esquemaEtapas.safeParse(etapasComNovoValor);
if (!validacao.success) {
  throw new Error(primeiraMensagemDeErro(validacao));   // acoes.ts:409-410
}
```

But the `catch` block only special-cases `EncomendaNaoEncontrada` — every other error, including
this deliberately-thrown validation error, is logged and **rethrown**, never converted to
`{ ok: false, erro }`:

```ts
} catch (erro) {
  if (erro instanceof EncomendaNaoEncontrada) {
    return { ok: false, erro: MENSAGEM_ENCOMENDA_NAO_EXISTE };
  }
  console.error("Falha ao ajustar etapa:", erro);
  throw erro;                                            // acoes.ts:439
}
```

This directly contradicts the file's own comment a few lines above ("passar de 365 é recusado
pelo `esquemaEtapas` logo abaixo, **com a mensagem em português**") — the message never reaches
the client, because the thrown error propagates as an unhandled rejection instead.

On the client, `AjusteRapidoEtapa.aplicar()` awaits this call and only calls `setPendente(false)`
*after* the await resolves:

```ts
setPendente(true);                                              // passo 2
const resposta = await ajustarEtapaEncomenda({ encomendaId, etapa, ...entrada }); // throws
setPendente(false);                                              // never reached
```

Since `aplicar` is invoked as `void aplicar(...)` from the button `onClick`, a thrown error here
becomes an unhandled promise rejection: no `toast.error` is shown, and the `+`/`-` buttons stay
`disabled={pendente || ...}` with the spinner (`Loader2`) spinning forever for that control,
until the user reloads the page.

The UI's client-side guard (`disabled={pendente || espera === 365}`) prevents a *single* browser
tab from triggering this through normal clicking, but it does not prevent it across two
concurrent sessions (this app's 3-5 managers can plausibly have the same encomenda open at once):
manager A pushes `esperaDias` to 365 first; manager B's tab, still showing 364 locally, is not
disabled and sends `deltaEspera: 1`, which the server-side `for update` read resolves against the
now-committed 365, computing 366 and hitting this exact path. There is no unit or e2e test
covering this boundary (`grep` for `365`/`deltaEspera` in `tests/e2e/encomendas-detalhe.spec.ts`
finds no hits).

**Fix:** give this validation failure the same treatment as `EncomendaNaoEncontrada` — a
dedicated error type (or reuse a `class LimiteInvalido extends Error {}`) caught explicitly and
turned into `{ ok: false, erro }`:

```ts
class AjusteInvalido extends Error {}

// ...inside the transaction:
const validacao = esquemaEtapas.safeParse(etapasComNovoValor);
if (!validacao.success) {
  throw new AjusteInvalido(primeiraMensagemDeErro(validacao));
}

// ...in the catch block:
} catch (erro) {
  if (erro instanceof EncomendaNaoEncontrada) {
    return { ok: false, erro: MENSAGEM_ENCOMENDA_NAO_EXISTE };
  }
  if (erro instanceof AjusteInvalido) {
    return { ok: false, erro: erro.message };
  }
  console.error("Falha ao ajustar etapa:", erro);
  throw erro;
}
```

## Warnings

### WR-01: Production migration runbook's D-10 guard doesn't check the invariant the migration itself introduces

**File:** `docs/operacao/06-migracao-espera-dos-marcos.md:36-49` (Passo 1)

**Issue:** `0009_espera-dos-marcos.sql` replaces `marcos_zero_ou_um` (which allowed `dias in (0,
1)` for markers, i.e. the old on/off switch) with `marcos_sempre_um_dia` (`dias = 1`, no
exceptions). Adding a `CHECK` constraint in PostgreSQL validates **all existing rows** at ALTER
time and aborts the whole migration (rolling back inside the same transaction) if any row
violates it. A marker row left at `dias = 0` under the old switch model — entirely possible
under `marcos_zero_ou_um` — would have made Step 4 fail outright.

The runbook's only pre-flight guard (Passo 1, "A guarda de D-10") checks whether any encomenda
*looks like real client data* ("nome ou cliente que você reconheça como real"); it never queries
`encomenda_etapas` for the specific condition that would break this specific migration
(`dias <> 1` on a marker row). The guard's actual question ("is this real customer data?") is
orthogonal to the risk ("would this ALTER TABLE fail?") — the runbook happens to be safe only by
inference, not by direct verification. (Not a live defect — the migration has already been
applied successfully in production — but the gap remains in the document for future re-reads /
future migrations that touch this table.)

**Fix:** add an explicit query to Passo 1 or Passo 3:
```bash
docker compose exec postgres psql -U amassa_owner -d amassa -c \
  "select id, encomenda_id, etapa, dias from encomenda_etapas where etapa in ('queima1','queima2','entrega') and dias <> 1;"
```
"O que você deve ver: nenhuma linha. Se alguma linha aparecer, **pare aqui** — a migração vai
falhar no Passo 4."

### WR-02: New "espera" counter is not exposed to assistive technology

**File:** `components/amassa/encomendas/ajuste-rapido-etapa.tsx:109-117` (marker/espera branch) and `:162-170` (interval/dias branch, pre-existing pattern reused here)

**Issue:** The project context for this review specifically calls out the new "espera antes do
marco" quick-adjust control as a new interactive surface to check for accessibility. The numeric
value display is marked `aria-hidden="true"`:

```tsx
<span
  className="text-mono tabular-nums flex w-6 items-center justify-center text-tinta"
  aria-hidden="true"
  data-testid={`ajuste-numero-espera-${etapa}`}
  data-pendente={pendente ? "true" : "false"}
  data-valor={espera}
>
  {pendente ? <Loader2 className="size-4 animate-spin" aria-hidden="true" /> : espera}
</span>
```

The `+`/`-` buttons only carry static labels ("Diminuir/Aumentar a espera antes de {etapa}")
that never include the current or resulting value. A screen-reader user pressing these buttons
gets no indication of what the count was, or what it became, after activation — the only
accessible surface is the disabled state of the buttons themselves.

**Fix:** either drop `aria-hidden` and give the span an accessible name that includes the
current value and unit (e.g. `aria-label={`Espera atual: ${espera} dias`}`), or add a visually
hidden live region (`aria-live="polite"` + `sr-only`) that announces the new value once
`aoConfirmar`/the state settles, e.g.:
```tsx
<span className="sr-only" aria-live="polite">
  {pendente ? "Salvando…" : `Espera atual: ${espera} ${espera === 1 ? "dia" : "dias"}`}
</span>
```

### WR-03: `TrilhaEtapas` can show two different "conclusion" dates on the same screen after concluding

**File:** `components/amassa/encomendas/trilha-etapas.tsx:107-168`

**Issue:** `duracaoTotalEmDias`/`dataDeConclusao` (rodapé) are seeded once from the `cronograma`
prop via `useState` and only update when one of the six `AjusteRapidoEtapa` controls confirms a
server response (`aoConfirmar`). The situação line (`textoDaSituacao(situacaoAtual)`), by
contrast, is recomputed from `conclusaoConfirmada` once "Marcar como concluída" succeeds. Because
the component never remounts on `router.refresh()` (a documented, deliberate choice to work
around a measured refresh-delivery failure rate), a user who concludes an encomenda and then
still touches one of the six quick-adjust controls will see the rodapé's "Conclusão prevista"
update to a freshly recalculated date while the situação line above continues to show
`Concluída em {a different, earlier date}` — two conflicting dates on the same screen. This is
called out at length in the component's own comments as a known, deliberately-deferred issue
("DERIVA CONHECIDA... NÃO corrigida aqui"), so the team is aware of it, but it was not in the
reviewer's `<known_context_do_not_report>` list and remains a real, user-visible inconsistency
that a future pass should close (e.g. by disabling the six `AjusteRapidoEtapa` controls once
`statusAtual` is a final state, or by keying the whole subtree so it remounts after conclusion).

**Fix:** simplest correct option — once `!podeConcluir`, render the six `AjusteRapidoEtapa`
controls as read-only (no buttons), so the rodapé's derived state can no longer drift from the
situação line post-conclusion. This is a product-facing behavior change, so it should be
confirmed with the owner before implementing, per the component's own comment.

## Info

### IN-01: Marker rows' `dias` field is never registered by the form — implicit trust with no client-side guard

**File:** `components/amassa/encomendas/formulario-encomenda.tsx:362-401`

**Issue:** `EtapaDoFormulario` only calls `register(...)` on `etapas.${indice}.esperaDias` for
marker rows — `etapas.${indice}.dias` is never registered for the three markers, so its value
travels through the form purely as whatever `valoresIniciais()` seeded (`DIAS_PADRAO`'s `1` on
create, or `linha.dias` from the database on edit) with no UI path to see or correct it if it
were ever wrong. This is safe today because the DB/Zod invariant guarantees marker `dias === 1`
at write time, so no bad value should ever reach `valoresIniciais()` — but it does mean a future
regression that puts a marker row at `dias !== 1` in the database (e.g. a bulk data fix that
misses the constraint, or a future migration bug) would silently round-trip through this form
with no visual indication anything is wrong, since the field genuinely isn't rendered at all for
markers.

**Fix:** no action required now; if this module ever needs a defensive display, a
`disabled`/read-only rendering of `dias` for markers (e.g. "Sempre 1 dia") would make the
invariant visible instead of implicit.
