## Pattern Assignments

### `lib/auth/rotas-publicas.ts` — verified, not just claimed

Full file (11 lines, quoted in full above from the read):
```typescript
// Módulo puro, sem nenhum import: a regra que decide se um caminho pode ser acessado sem
// sessão. É o único módulo que `lib/auth/auth.config.ts` consulta para proteger rotas —
// mantê-lo puro é o que permite testar a regra sem subir middleware nem servidor
// (`tests/unit/rotas-publicas.test.ts`).
export const ROTAS_PUBLICAS = ["/login", "/api/health"];

export function ehRotaPublica(caminho: string): boolean {
  return ROTAS_PUBLICAS.some(
    (prefixo) => caminho === prefixo || caminho.startsWith(`${prefixo}/`),
  );
}
```
Confirmed: zero imports, exactly the two exports CONTEXT.md claims. `lib/auth/auth.config.ts` calls `ehRotaPublica(request.nextUrl.pathname)` in its single `authorized()` callback (line 47) — it is indeed the only consumer for authorization purposes. **This is the seam for D-03.** Since the whole platform moves to `/gestao` and root becomes public with no session, the likely change is inverting the model: instead of listing public routes under a root that's mostly protected, either (a) keep `ROTAS_PUBLICAS` but add `/` and every future site path (risk: list grows with every site section, exactly what D-01 forbids for redirects — but this list is different, it's fine since site pages aren't code-listed one by one, just the prefix `/` handles it if root pages don't nest under a protected prefix), or (b) flip logic so `middleware.ts`'s `matcher` only targets `/gestao/*` (simpler, matches D-03 "proxy protects only /gestao" literally). **Recommend option (b)**: change `middleware.ts`'s `config.matcher` to `["/gestao/:path*"]` (plus whatever `/gestao/login` needs) rather than growing `ROTAS_PUBLICAS`. Planner must decide and document explicitly — this is a locked decision (D-03) about behavior, not about which file, so whichever file is touched, the "only consult this one module" property must survive.

### `middleware.ts` (root) — quoted in full above

Key excerpt, the part every route-move plan must not break (lines 68-73):
```typescript
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|api/auth).*)"],
};
```
This currently matches almost everything. Moving to `/gestao` scoping means either narrowing this matcher to `/gestao/:path*` (and `/api/...` if any API needs auth under `/gestao`) or keeping it broad and relying purely on `ehRotaPublica` returning `true` for the site's paths. Given D-03 ("o proxy protege só `/gestao`"), narrowing the matcher is the literal reading and the safer one (site pages never even enter the Auth.js `authorized()` callback). `ehRotaDeApiNaoPublica`, `podeRenovarSessao`/`semRenovacaoDaSessao`, and the no-store cache header logic (lines 24-61) all key off `ehRotaPublica` — if the matcher narrows to `/gestao/*`, these become unreachable for site routes automatically (no change needed inside the function body), which is the cleanest and lowest-risk shape.

### `lib/precificacao/navegacao.ts` — quoted in full above, "the pattern to imitate"

Shape to copy verbatim for a `/gestao` URL module (e.g. `lib/rotas/gestao.ts` or wherever the redirect/URL-building module lands):
```typescript
export type DestinoDaAbaPecas = { peca?: string | null; apagarPeca?: string | null; aviso?: string | null; mostrarExclusivas?: boolean; };

export function hrefDaAbaPecas(destino: DestinoDaAbaPecas = {}): string {
  const parametros = new URLSearchParams({ aba: "pecas" });
  if (destino.peca) parametros.set("peca", destino.peca);
  // ... one `if` per optional param, then:
  return `/financeiro?${parametros.toString()}`;
}
```
Apply this shape to (1) the "Paguei/Recebi → Caixa, parcela específica" destination (D-06) — a `hrefDoCaixa({ parcela })` function living probably in `lib/financeiro/navegacao.ts`, and (2) any WhatsApp URL builder for the site (`lib/site/whatsapp.ts::hrefDoWhatsapp(numero, mensagem)` using `URLSearchParams`-style escaping, not raw string concatenation, matching D-17's `wa.me/<numero>?text=<mensagem>` requirement). Also usable for the old-address redirect table if it needs to build the mapped new URL rather than just declare a static list.

### `middleware.ts` interplay with route move

Already covered above — the critical file for the D-21 "rotas primeiro" plan. `NextResponse.json({ erro: "Não autorizado." }, { status: 401 })` for non-public API routes (line 47) and the `Cache-Control: no-store` header for protected pages (line 60) both key off `ehRotaPublica`, so whichever seam is chosen (narrower matcher vs. broader `ROTAS_PUBLICAS`), these two behaviors must keep working identically for everything under `/gestao`.

### `app/(app)/` route group — real segment vs. route group

Current idiom is a **route group** `(app)` that maps to `/` (parenthesized segments are invisible in the URL). The existing precedent for a *named, visible* segment is `app/(auth)/login` → `/login` (auth group also invisible, but its child `login` folder is a real path segment). **For `/gestao`, the existing idiom does not have a precedent for a group mapping to a visible prefix** — Next.js route groups by definition never appear in the URL. The planner should almost certainly rename the directory from `app/(app)/` to a real segment `app/gestao/` (dropping the parentheses), moving every child folder (`abertura`, `agenda`, `cadastros`, `conta`, `encomendas`, `estoque`, `financeiro`, plus `page.tsx`/`error.tsx`/`loading.tsx`/`not-found.tsx`) under it unchanged, and `app/(auth)/login` becomes `app/gestao/login` (or stays a sibling group under `gestao`, e.g. `app/gestao/(auth)/login`, if the plan wants to keep login visually separate from the shell layout — current `app/(app)/layout.tsx` wraps the shell only for its own group, and `login` lives in a sibling group specifically to avoid the shell chrome, so this separation should be preserved: `app/gestao/(auth)/login` + `app/gestao/(app)/...` is the closest-fidelity move).

### Root `app/page.tsx`, `app/not-found.tsx`, `app/layout.tsx` — the new public site

`app/not-found.tsx` (quoted in full above) is today's only precedent for a page living outside the protected group, safe from session and DB. Its own comment (lines 13-15) is the exact statement of the isolation rule D-15/D-03 need: "por ficar fora do grupo protegido, este arquivo nunca pode exibir dado de sessão — só copy estática." The new `app/page.tsx` (public site) should follow the same placement (directly in `app/`, not nested under any group that has a layout reading session) and the same "static only" discipline. `app/layout.tsx` (root, quoted above) already loads both fonts via `next/font/google` with CSS variables on `<html>` — the site's Fraunces font can be added the same way (a third `next/font/google` call, third CSS variable), but D-19 requires the site's neutrals to live in **their own named `:root` block**, separate from the platform's tokens in `app/globals.css` — this is a new CSS pattern, not extending the existing token block; the closest existing precedent is `app/globals.css`'s existing `@theme`/`:root` variable block (worth having the planner read that file directly at plan time, not paraphrase it here).

### `db/schema.ts` — singleton table precedent

Two existing singleton tables, both quoted in full above: `aberturaConfiguracao` and `configuracaoFinanceira`. Shared shape:
```typescript
linhaUnica: boolean("linha_unica").notNull().default(true),
// ...
(tabela) => [
  unique("..._linha_unica_uk").on(tabela.linhaUnica),
  check("..._linha_unica", sql`${tabela.linhaUnica}`),
],
```
This is the pattern to copy for `anotacoes_da_casa` (one-row table, D-08): a `linhaUnica` boolean with a unique constraint + check constraint guaranteeing exactly one row ever exists at the database level (not just application discipline). **Gap:** neither existing singleton table has an authorship column (`salvo_por`) or an optimistic-concurrency / stale-write column. D-08 needs both: "quem salvou por último e quando" (a `salvoPorId` FK to `usuarios` + reuse of the existing `atualizadoEm` timestamp convention already in every table) and a stale-write warning (comparing the client's last-seen `atualizadoEm` against the server's current value before an overwrite — no existing precedent for this comparison anywhere in the codebase; it will be new logic, likely a pure function in `lib/anotacoes/consultas.ts` or similar, following the "regra de negócio em módulo puro" convention).

## Shared Patterns

### Authorization (`exigirUsuario()` first line)
**Source:** `lib/auth/exigir-usuario.ts`, applied in `app/(app)/layout.tsx` line 15 and `app/(app)/page.tsx` line 16.
**Apply to:** every Server Action and every page under the moved `/gestao` tree — no page in this phase's scope changes this rule. The public site's `app/page.tsx` and any site-only helper (`lib/site/whatsapp.ts`) must **never** import this or anything that transitively reaches it (D-15's isolation guarantee).

### Error containment per block (not per page)
**Source:** `app/(app)/page.tsx` (`falhaAoCarregarFornos` pattern, quoted above).
**Apply to:** all 5 Início blocks (D-09) — each needs its own try/catch, its own boolean flag, its own `EstadoErro` render, never a shared page-level catch.

### Pure URL-building modules
**Source:** `lib/precificacao/navegacao.ts` (quoted in full above).
**Apply to:** `lib/financeiro/navegacao.ts` (Caixa/parcela destination, D-06), `lib/site/whatsapp.ts` (wa.me links, D-17), and possibly the old-address redirect table if it needs computed rather than static targets.

### Navigation single source of truth
**Source:** `lib/navegacao/itens.ts` (quoted in full above).
**Apply to:** `barra-inferior.tsx`, `barra-lateral.tsx`, `cabecalho-movel.tsx` — all three already consume this one module; no new module needed, only its contents change.

### Empty/error/loading states on every screen
**Source:** `components/amassa/estado-vazio.tsx`, `estado-erro.tsx`, `app/(app)/loading.tsx` (all quoted above).
**Apply to:** every Início block (D-09) and the public site's "sem Agenda" state (D-16) — though the latter is fully static content, not a data-driven empty state, so it likely doesn't reuse `EstadoVazio` (that component is Server-Component-with-props for the *authenticated* shell; the site has its own layout with no shell at all).
