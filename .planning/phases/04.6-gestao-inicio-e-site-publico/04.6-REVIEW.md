### CR-02: Anotações — a pending save is cancelled on unmount while the indicator still reads "salvo" (silent data loss)

**File:** `components/amassa/inicio/editor-de-anotacoes.tsx:67-73, 107-118, 189-195`

**Issue:**
`aoDigitar` never changes `indicador`. After the first successful save the indicator stays at
"salvo" while the user keeps typing. The unmount cleanup then *clears* the debounce timer instead of
flushing it.

Scenario (phone, studio):
1. Type a note and wait for "salvo".
2. Add "comprar argila" and, within 1.2 s, tap "Financeiro" in the bottom bar.
3. `EditorDeAnotacoes` unmounts and `clearTimeout` drops the save.

The last words never reach the server, and the screen said "salvo" the whole time. The same happens
on tab close, since there is no `pagehide`/`visibilitychange` flush. The comment at lines 28-32
("curto o bastante para a pessoa não perder o texto…") promises a guarantee the code does not give.

**Fix:**
- Mark dirty on keystroke: `setIndicador("parado")`, or a new `"pendente"` state with its own label.
- Flush instead of dropping, on unmount and on page hide:
```tsx
const pendenteRef = useRef<{ texto: string } | null>(null);
function aoDigitar(valor: string) {
  setTexto(valor); setConflito(null); setIndicador("pendente");
  pendenteRef.current = { texto: valor };
  if (timeoutRef.current) clearTimeout(timeoutRef.current);
  timeoutRef.current = setTimeout(descarregar, PAUSA_DE_DIGITACAO_MS);
}
function descarregar() {
  if (timeoutRef.current) clearTimeout(timeoutRef.current);
  const p = pendenteRef.current; pendenteRef.current = null;
  if (p) void salvar(p.texto, vistoEmRef.current);
}
useEffect(() => {
  const aoEsconder = () => { if (document.visibilityState === "hidden") descarregar(); };
  document.addEventListener("visibilitychange", aoEsconder);
  window.addEventListener("pagehide", descarregar);
  return () => { document.removeEventListener("visibilitychange", aoEsconder);
                 window.removeEventListener("pagehide", descarregar); descarregar(); };
}, []);
```

### CR-03: Anotações — stale `vistoEm` closure makes a user conflict with their own save

**File:** `components/amassa/inicio/editor-de-anotacoes.tsx:107-118` (the closure at line 116), `75-88`

**Issue:**
The debounce callback captures the render-scoped `vistoEm` from the keystroke that scheduled it.
Scenario:
1. The user types "abc" and pauses 1.2 s. `salvar("abc", V0)` goes out.
2. On a slow 4G link, the user types "d" while that request is still in flight.
3. The timer for "d" is created in a render where `vistoEm` is still `V0`.
4. The first save returns and sets `vistoEm = V1`. 1.2 s later the second timer fires `salvar("abcd", V0)`.
5. The server row is at `V1`, so `decidirGravacao` returns `"avisar"`.

The user is told "Alguém salvou um texto diferente enquanto você escrevia" about their own write,
and "ver o dela" would discard "d". The server logic is right; the client sends the wrong version.

Related, and safe but misleading: after a conflict, `aoDigitar` hides the warning (line 111). The next
autosave still sends the old `vistoEm`, so the warning comes back. The comment at lines 109-110 ("a
próxima gravação automática já resolve") is false.

Next's action queue appears to serialize Server Actions, so two in-flight saves from one tab should
not reorder. That is suspected, not confirmed; this finding does not depend on it.

**Fix:** Keep the version in a ref, read it when the save fires, and never overlap saves:
```tsx
const vistoEmRef = useRef<string | null>(atualizadoEmInicial || null);
// on ok:         vistoEmRef.current = resposta.atualizadoEm;
// in verODela:   vistoEmRef.current = conflito.atualizadoEm;
// in manterOMeu: salvar(texto, conflito.atualizadoEm)   (unchanged)
// timer:         setTimeout(() => void salvar(valor, vistoEmRef.current), …)
```
Plus a single-flight guard. While a save is running, remember only the latest text and send it
after the running save resolves, using the updated ref.

### CR-04: Início "Produção" shows late orders as "Em espera"

**Files:** `lib/encomendas/producao-em-andamento.ts:77-83`, `components/amassa/inicio/bloco-producao.tsx:97-112`

**Issue:**
`situacaoEm` returns `{ tipo: "atrasada", dataPrevista, diasDeAtraso }` (`lib/encomendas/cronograma.ts:113, 337`).
`producaoEmAndamento` sends `"atrasada"` (and `"nao-comecou"`) to `default`, giving
`etapaAtual: null`. `BlocoProducao` renders **every** `etapaAtual === null` as the "Em espera" tag.

So an order past its delivery date, the single most actionable line a production glance can show,
appears on the Início as "Em espera" with no further text. `listarEncomendasAtivas()` includes
`em_producao` orders, so this is reachable in normal use, not a defensive branch.

**Fix:** Carry the situation kind through, and render it:
```ts
// producao-em-andamento.ts
export type LinhaDeProducao = { …; atrasoDias: number | null; aindaNaoComecou: boolean };
case "atrasada":    return { id, titulo, etapaAtual: null, proximaEtapa: null, diasAteProxima: null, atrasoDias: situacao.diasDeAtraso, aindaNaoComecou: false };
case "nao-comecou": return { …, atrasoDias: null, aindaNaoComecou: true };
```
In the block, show a red "Atrasada · N dias" tag (tokens `bg-erro-fundo text-erro`) for `atrasoDias`,
"Começa em …" for not-started, and "Em espera" only for `em-espera`. Add both cases to the unit test.

### WR-02: Site-wide smooth scrolling leaks into the platform and animates every `/gestao` navigation

**File:** `app/globals.css` (the new `@media (prefers-reduced-motion: no-preference) { :root { scroll-behavior: smooth; } }`), `app/layout.tsx:57`

**Issue:** `globals.css` is shared by both surfaces, so the rule meant for the site's anchor links
also applies under `/gestao`. In Next 16 the router only suspends smooth scrolling during route
transitions when `<html data-scroll-behavior="smooth">` is present. Evidence:
`node_modules/next/dist/shared/lib/router/utils/disable-smooth-scroll.js`: `if (!hasDataAttribute) { … fn(); return; }`.
The attribute is absent (grep of `app/` finds none).

Result: every platform navigation from a scrolled list now animates to the top, and the Caixa's
`scrollIntoView({block:"center"})` animates too. That is a visual change to existing modules,
outside this phase's stated boundary.

**Fix:** Add `data-scroll-behavior="smooth"` to the `<html>` in `app/layout.tsx`. Or scope the rule to
the site: put it on the site wrapper, or apply it via a class that only `app/page.tsx` sets.

### WR-03: Início is never revalidated after `salvarAnotacoes`, so a restored Início may seed the editor with pre-save props (suspected, not confirmed)

**File:** `lib/anotacoes/acoes.ts:99-109`, `components/amassa/inicio/editor-de-anotacoes.tsx:52-58`

**Issue:** `salvarAnotacoes` calls no `revalidatePath`. `EditorDeAnotacoes` seeds `useState` from
props exactly once. Suspected scenario:
1. The user saves notes, goes to Financeiro, then presses the browser back button.
2. If the router restores `/gestao` from its client cache (the documented back/forward behaviour of
   the App Router cache), the editor remounts with the **old** `textoInicial`/`atualizadoEmInicial`.
3. The textarea shows text from before the user's own edit, and the next keystroke triggers a
   conflict against their own save.

I could not confirm how Next 16.3.5's segment cache handles back/forward here without running the
app, so this is reported as suspected.

**Fix:** `revalidatePath(rotaDeGestao("/"))` after a successful write, which also purges the client
router cache. Alternatively, re-read the sheet on mount via a small read action (with
`exigirUsuario()` first) when `document.visibilityState` returns to visible.
